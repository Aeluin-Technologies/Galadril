Galadril Documentation

Introduction to Galadril

Welcome to the technical documentation for Galadril.

Galadril is a scalable, configuration-driven platform designed to ingest heterogeneous data, such as documents, financial logs, and OSINT, and process it through high-performance, custom machine learning pipelines.

Core Philosophy

  • Configuration-Driven: Orchestrate your entire system via a single connectors.yaml service settings and versioned pipeline definitions for reproducibility.
  • Event-Driven Architecture: High-throughput communication between components is handled natively via Apache Kafka.

Prerequisites

To effectively build with Galadril, you should be familiar with the following core technologies:

TechnologyPurpose in Galadril
YAMLPipeline config for services.
PythonCustom ML models (JAX, PyTorch, etc.) via galadril-vision.
AvroData schemas and service interoperability.

TIP: Since these are industry-standard languages, LLMs have excellent support for them. If you run into schema issues or need boilerplate code, use them to speed up your workflow.

Pipeline Configuration

Docker Compose mounts infrastructure/docker/connectors.yaml. Kubernetes and k3s use infrastructure/kubernetes/connectors.yaml, with Service DNS and mesh transport. Deployed services receive an explicit connector path; their fallback is /etc/galadril/connectors.yaml, independent of the source checkout. The standalone DAG in infrastructure/configuration/pipeline.yaml is a test configuration. Production tenant pipelines are authored and published through Gateway to Registry.

See Pipeline storage and revision control for defaults, production deployment, tenant isolation, and migration from S3.

Connector

connectors defines infrastructure credentials for external services.

name: connector_example

registry:
  endpoint: "http://127.0.0.1:50054"

connectors:
  # Streaming ingestion for incoming events.
  kafka:
    brokers: ["redpanda:9092"]
    schema_registry: "http://redpanda:8081"
    consumer_group: "intake-service"

  # Storage for processed raw documents.
  s3:
    endpoint: "http://rustfs:9000"
    access_key: "minioadmin"
    secret_key: "minioadmin"
    region: "us-east-1"
    bucket: "lake"
    bucket_notifications: "s3-bucket-notifications"

  # Persistent storage.
  postgres:
    database: "galadril_dev"
    host: "postgres:5432"
    user: "postgres"
    password: "postgres"

This example targets the supplied Docker Compose deployment. Its registry.endpoint is the application’s local Envoy egress listener, not the Registry container or the Docker host. All local application services use network_mode: service:api-proxy to share the single Envoy’s network namespace, including loopback. Envoy forwards to Registry on 127.0.0.1:50053. This shared namespace is one local trust domain; it does not provide workload isolation or internal mTLS. The other connector hostnames still resolve through the Docker network.

An Envoy in an ordinary separate Docker container is not reachable through this loopback address. Kubernetes and k3s use infrastructure/kubernetes/connectors.yaml, with Service DNS endpoints and transparent Istio Ambient interception. The supplied mesh policies require the shared waypoint and strict workload mTLS. See Kubernetes deployment and API proxy operation.

Registry is a top-level service setting. It shares connectors.s3 credentials and validates only caller-supplied tenants against S3 markers; no tenant list is configured or exposed.

1. Kafka Connector

  • brokers: A list of bootstrap servers (e.g., Redpanda or Apache Kafka).
  • schema_registry: The URL for the Confluent-compatible schema management service for managing data formats.
  • consumer_group: The logical identifier that allows multiple workers to share the processing load of a topic.

2. S3 (Object Storage) Connector

Used for storing and retrieving large binary objects like images, videos, or model weights.

  • endpoint: The API entry point. This allows for compatibility between local solutions like MinIO and cloud providers like AWS.
  • access_key / secret_key: The credentials required for secure authentication.
  • bucket_notifications: Defines the specific topic or queue where bucket events (like “Object Created”) are published.

Data keys use a tenant-first partition. Raw ingestion writes <tenant>/raw/<group>/<file>; Registry owns the _registry marker and _lakefs subtrees below the same tenant partition.

3. Postgres Connector

Manages relational data, system state, and metadata.

  • host: The network address and port of the database instance.
  • database: The specific database name for the application environment.
  • user / password: The credentials used to establish a secure database session.

Registry storage configuration

Application services configure the internal Registry gRPC endpoint at the top level of connectors.yaml:

registry:
  endpoint: http://127.0.0.1:50054

This address reaches the caller’s local Envoy egress listener. It works when the applications share the single Envoy’s network namespace through Docker Compose network_mode: service:api-proxy. Envoy forwards to Registry’s loopback listener on 127.0.0.1:50053. This local namespace is one trust domain with plaintext internal traffic. Kubernetes uses Service DNS and Istio Ambient for strict workload mTLS and source-specific policies; it does not use this loopback profile.

Registry reads connectors.s3 from the same file as other services. The connectors.s3.bucket must match its service-owned storage namespace. Raw lakeFS repository names, S3 paths, and storage namespaces are never accepted from gRPC callers. Registry also receives these deployment settings:

VariablePurpose
LAKEFS_ENDPOINTInternal lakeFS API endpoint
LAKEFS_ACCESS_KEY_IDRegistry-only lakeFS credential
LAKEFS_SECRET_ACCESS_KEYRegistry-only lakeFS secret
REGISTRY_STORAGE_NAMESPACEBucket-root S3 namespace used for tenant partitions
REGISTRY_REPOSITORY_PREFIXPrefix for hashed tenant repositories
REGISTRY_CONFIG_PATHShared connectors.yaml path
REGISTRY_BIND_ADDRRegistry gRPC listen address

Docker Compose runs lakeFS with S3 block storage backed by MinIO and mounts the same connector file into Registry, Gateway, Intake, and Vision. Kubernetes and k3s use the Ambient profile and separate workload connector Secrets. Registry receives registry-connectors and registry-runtime; lakeFS credentials are not mounted into API callers. Its application listener uses REGISTRY_PROXY_MODE=ambient and REGISTRY_BIND_ADDR=0.0.0.0:50053. Callers use http://registry.galadril.svc.cluster.local:50053; ztunnel and the shared waypoint authenticate, encrypt and authorize these calls. See Kubernetes deployment for external dependencies and the separate configuration profile.

Tenant lifecycle

ValidateTenants accepts one to 100 explicitly supplied, syntactically valid tenant IDs and reports whether each <tenant>/_registry/tenant.json marker exists in S3. It never enumerates tenants, and an empty request is invalid. Positive and negative marker reads use a bounded, ten-second Moka cache; tenant creation and deletion update or invalidate that cache. The registry does not query PostgreSQL. GetTenant and every artifact read fail when the marker is absent. PutTenant and artifact insert/update RPCs idempotently initialize an opaque lakeFS repository and S3 marker before their write path.

The bucket layout is tenant first:

<tenant>/raw/<group>/<file>
<tenant>/_registry/tenant.json
<tenant>/_lakefs/<lakeFS-managed blocks>

Inside the tenant lakeFS repository, Registry stores logical artifacts at ontology/state.json and pipeline/state.json. The _lakefs physical prefix is private to lakeFS; its block keys do not mirror logical repository paths.

DeleteTenant is reserved for GDPR erasure. The request must repeat the exact tenant ID in confirmation_tenant_id; Registry then removes the lakeFS repository record and the complete <tenant>/ S3 prefix, including raw data and the tenant marker. Deleting an ordinary pipeline or ontology never invokes this tenant purge.

The direct S3 permission exists because deleting a lakeFS repository does not delete its physical objects. Registry does not use S3 to bypass lakeFS for ontology or pipeline reads and writes.

Revisions and publication

Every successful Registry mutation creates a lakeFS commit. The immutable commit ID is the opaque revision returned to clients. Updates supply an expected revision, publications pin an exact revision, and Vision must request the same revision carried by its Kafka execution identity.

There is no application history API. Operators must not expose lakeFS commit logs as ontology or pipeline history. A future PostgreSQL history model will provide searchable audit semantics independently of storage versioning.

Initialization

No deployed state exists, so there is no legacy database migration or compatibility reader. Discard prototype databases and author the desired ontology documents, pipeline definitions, publications, and bindings through Registry; their first accepted writes establish the lakeFS revisions. The unshipped PostgreSQL pipeline prototype migration is removed rather than carried forward. Gateway migrations must never create ontology, pipeline, publication, or binding tables.

Data Sources & Routing

sources defines how raw files in S3 are caught and routed into Kafka.

sources:
  - id: image_source
    match_pattern: "^images/" # support Regexes!
    topic: raw_images
    schema_path: schemas/avro/image.avsc

Definition Fields

FieldTypeDescription
idStringUnique identifier for this source.
topicStringKafka topic where parsed data will be sent.
schema_pathString(Optional) Local path to an .avsc Avro schema.
match_patternString(Optional) Regex to identify where to stream.
parserStringSee Data Parsers.

How Routing Works

When a file arrives in S3 (e.g., s3://my-bucket/finance/january.csv), the Rust Ingestor must decide which source block to use.

1. Regex Matching (match_pattern)

If you define match_pattern: "^finance/.*\.csv$", the system will test the S3 key against this regex. If it matches, this source is selected.

2. Otherwise

If no match_pattern is defined, the system will reject the incoming source, and won’t process the raw data.

Required & Reserved Fields

While Avro is flexible, Galadril’s internal logic (especially the Python Vision service) expects specific fields to be present in the schema to properly link data back to its origin.

1. Unique Identifiers

Every record must have a unique ID. The system looks for these fields in order of priority to determine the Kafka partitioning key:

  1. event_id (Common for logs/financials)
  2. image_id (For satellite/photos)
  3. document_id (For PDFs/Docs)
  4. article_id (For OSINT/News)

2. Traceability Fields

To ensure the Python pipeline can download binary content, the following field is mandatory for metadata parsers:

  • storage_path (String): The full S3 URI.

Data Parsers

Once a file is routed to a source, the parser dictates how the file’s content is transformed before entering Kafka.

1. The metadata Parser (Default)

  • Behavior: Does not download the file. It generates a standard JSON payload containing the S3 URI, timestamps, and generated UUIDs.
  • Use Case: Images, Videos, PDFs. You don’t want 50MB images flowing through Kafka. You pass the reference (URI), and the Python Vision service will download it later.

2. The csv Parser

  • Behavior: Downloads the file from S3 and parses it line by line using the CSV headers. It emits one Kafka message per row. It automatically converts numerical strings to floats.
  • Use Case: Batch ingestion of financial transactions, lists of employees, or sensor logs.

3. The json Parser

  • Behavior: Downloads the file. If the file contains a JSON Array, it emits one Kafka message per item. If it’s a single JSON Object, it emits one message.
  • Use Case: OSINT data, scraped articles, or API data dumps.

Example

sources:
  - id: financial_data
    topic: raw.finance
    parser: csv
    match_pattern: "^finance/.*\\.csv$"
    schema_path: schemas/avro/finance.avsc

Pipeline (Steps)

pipeline defines a DAG for processing. It connects data sources to ML models, and ML models to other ML models.

Step Definition

FieldDescription
stepUnique name for this processing node (e.g., face_detection).
typeUsually inference for Galadril.
modelThe fully qualified Python class path.
artifact_pathWhere the model weights are stored on S3.
input_fromArray of IDs. Defines the dependencies of this step.
paramsKey-Value pairs passed to the model’s constructor.

Understanding input_from

The input_from array is the most important field. It tells the Python orchestrator where to get the data for this step.

You can reference:

  1. A Source ID: To process raw data directly from Kafka.
  2. Another Step ID: To chain models together.

Example: Chaining Models

In this example, the Face Recognition model waits for raw images, and the Database Storage step waits for the Face Recognition step to finish.

pipeline:
  # Step 1: Detect faces from raw images
  - step: face_detection
    type: inference
    model: my_models.FaceRecognition
    input_from: [image_source] # References a Source ID
    params:
      threshold: 0.85

  # Step 2: Store results in the database
  - step: database_sink
    type: storage
    model: my_models.PostgresSink
    input_from: [face_detection] # References the previous Step ID

Model Details

1. BGE-M3 (bge_m3)

Versatile embedding model that supports multi-functionality, multi-linguality, and multi-granularity. It performs simultaneous dense, sparse (lexical), and multi-vector (ColBERT) retrieval.

  • Inputs:
    • text (Required): The string content to be embedded.
  • Outputs:
    • dense: A high-dimensional vector for semantic similarity.
    • sparse: A dictionary of token weights for lexical/keyword matching.
    • colbert: A multi-vector representation for fine-grained late interaction scoring.

2. Face Recognition (face_recognition)

Performs facial detection, alignment, and embedding extraction.

  • Inputs:
    • action (Required): The inference action to perform (from FaceAction).
    • image (Required): BGR image as numpy array (H, W, 3).
  • Outputs:
    • faces_count: Number of detected faces.
    • faces: List of objects containing bbox, keypoints, confidence, and the 512-d embedding.

3. GOT OCR (got_ocr)

General Object Role-playing OCR for high-quality text extraction.

  • Inputs:
    • image / images: Single ndarray or list of images.
    • action: Specific OCR task (from GotOcrAction).
    • format: Boolean (default True) to maintain formatting.
    • box: Optional crop area [x1, y1, x2, y2].
  • Outputs:
    • text: The extracted string content.

4. Grounded SAM (grounded_sam)

Combines language understanding with precise image segmentation.

  • Inputs:
    • image & text (Required): The source image and the prompt to segment.
    • threshold: Detection confidence (default 0.2).
    • return_masks: Whether to return the binary segmentation masks.
    • Note: Supports tiling for high-resolution images via use_tiling.
  • Outputs:
    • total_objects: Count of all detected instances.
    • concepts: Dictionary mapped by label containing box, score, and optionally mask.

5. OWLv2 (owlv2)

Open-world localized vocabulary object detection.

  • Inputs:
    • image & text (Required): Image and query labels.
    • threshold: Detection sensitivity (default 0.1).
  • Outputs:
    • concepts: Detailed instances per label with box and score.

6. SigLIP 2 (siglip2)

State-of-the-art vision-language model for creating shared embeddings.

  • Inputs:
    • action (Required): embed_image or embed_text.
    • image: Required for image embedding.
    • text: Required for text embedding.
  • Outputs:
    • embedding: Vector representation.
    • embedding_dim: Size of the vector.

7. TimesFM Forecast (timesfm_forecast)

Foundation model for time-series forecasting with external covariates.

  • Inputs:
    • history (Required): List of numerical historical values.
    • horizon: Number of future steps to predict (default 24).
    • dynamic_numerical_covariates: Optional dict for external regressors.
  • Outputs:
    • point_forecast: The predicted mean values.
    • quantiles: Deciles (0.1 to 0.9) for uncertainty estimation.

8. Whisper (whisper)

Multilingual speech-to-text with advanced speaker diarization.

  • Inputs:
    • audio (Required): Dict containing waveform (ndarray) and sample_rate.
    • task: transcribe or translate (default transcribe).
    • language: Optional ISO language code.
    • enable_diarization: Boolean to trigger speaker clustering and embeddings.
  • Outputs:
    • text: Full transcript string.
    • chunks: Segments with timestamp, text, speaker, and speaker_embedding.
    • language: Detected or used language.

Galadril telemetry contract

Galadril binaries use OpenTelemetry SDKs and send logs, metrics, and traces to the intermediary collector exclusively with OTLP over gRPC. Application containers do not expose scrape endpoints and do not select observability backends. Exporters use bounded queues and background workers; queue overflow drops telemetry instead of delaying application work.

Resource attributes

Every signal carries these lowercase resource attributes:

AttributeExample
service.namegaladril-intake
service.version0.1.1
deployment.environmentproduction
service.instance.idcontainer hostname
telemetry.sdk.languagerust or python

service.name is stable across worker roles so traces, metrics, logs, and profiles join on the same value. Instance and role data belong in separate attributes rather than in the service name.

Structured events

Every log record has an event.name containing a lowercase dot-notation identifier with at least two segments, for example auth.login or kafka.message.failed. The record body is a distinct, lowercase explanatory phrase. Attribute names are lowercase and use OpenTelemetry semantic conventions where one exists.

Do not place tenant IDs, entity IDs, paths, trace IDs, or other unbounded values on metrics. Those values can be log or span attributes when operationally necessary.

Rust request paths register their instruments during service startup and emit http.server.request.count, http.server.request.duration, messaging.process.count, and messaging.process.duration without allocating metric labels dynamically. Python process and pipeline instruments use the same OTLP metric pipeline.

Propagation

W3C traceparent is the canonical propagation format. HTTP ingress extracts it before starting server spans. Kafka and Ray producers inject it into their carriers, and consumers restore it before starting consumer spans.

Continuous profiling

Grafana Alloy profiles the Rust and Python containers out of process with the OpenTelemetry eBPF profiler. It samples at 19 Hz and ships a pprof-compatible batch every 30 seconds to the central Pyroscope service. Python process memory, virtual memory, garbage collection, CPU, and thread measurements are collected as asynchronous OpenTelemetry metrics, allowing profile windows to be aligned with memory or CPU changes without adding work to the application event loop.

The continuous pprof stream is a CPU profile. The eBPF profiler does not support allocation profiles; keeping malloc or Python allocator uprobes permanently enabled would also violate the production overhead constraint. Use the memory and garbage-collection metrics to select a narrow investigation window, then run an explicitly enabled allocation-profile session for that window. Do not describe process-memory metrics as allocation stack profiles.

The eBPF profiler requires a Linux host, the host PID namespace, and the kernel capabilities configured in infrastructure/docker/observability.yaml. Docker Desktop hosts that do not expose Linux eBPF facilities will run the remaining telemetry pipeline but cannot produce profiles.

Environment

Applications use the standard OTEL_EXPORTER_OTLP_ENDPOINT, OTEL_EXPORTER_OTLP_PROTOCOL=grpc, OTEL_TRACES_SAMPLER, and OTEL_TRACES_SAMPLER_ARG variables. DEPLOYMENT_ENVIRONMENT supplies the environment resource value for Rust; validated pipeline telemetry configuration supplies it for Python.

Operating the local API proxy

Docker Compose runs one Envoy process named api-proxy. Gateway, Registry, Intake, Vision and Scribe share its network namespace with network_mode: service:api-proxy. Their application listeners bind to loopback; only Envoy’s public TLS/JWT listener is published. This keeps local development lightweight without installing a mesh control plane or a proxy per service.

The local application namespace is one trust domain. Applications can reach each other’s loopback listeners, so Compose does not enforce cryptographic isolation between compromised workloads. Use the Istio Ambient deployment for workload identities, strict mTLS, and source-specific API policies. Ambient uses node tunnels and a shared waypoint, which provide more than a single proxy.

Configure TLS and JWT

Create disposable certificates using the native OpenSSL 3 CLI. On a Nix-managed host, enter nix shell nixpkgs#openssl first if openssl version reports LibreSSL:

bash infrastructure/envoy/dev-certificates.sh .local/identity

Run this before starting Compose. The proxy requires existing certificate, key, CA files; missing sources fail at mount setup. If an earlier Compose run created empty directories, remove only those empty placeholders before generating certificates:

rmdir .local/identity/gateway .local/identity/registry .local/identity
rmdir .local/jwks.json

rmdir refuses nonempty directories. Preserve existing identities and provider keys; use the path overrides below when they are managed elsewhere.

The shared proxy mounts Registry’s server identity at /etc/envoy/identity and Gateway’s public certificate/key at /etc/envoy/public. Applications receive neither directory. Never mount the CA signing key. The development CA lasts 365 days and leaf certificates last 30 days; clients must trust the development CA explicitly. Renew before expiry without changing private keys or application data:

bash infrastructure/envoy/dev-certificates.sh .local/identity --renew

Renewal validates the full replacement set before updating files and preserves the previous identity directory in a private sibling backup. Restart Envoy and Node TLS consumers afterwards. If the browser pins the old CA certificate, import the renewed CA into its trust store. Never disable certificate verification to restore sign-in. An expired local CA can interrupt JWKS retrieval even while an access token remains valid; authentication dependency outages return 503 and preserve the sealed session, whereas invalid or revoked credentials remain definitive denials. Access tokens keep the configured 15-minute lifetime.

Configure the free self-hosted Polis/Hydra SSO stack. The shared Compose proxy fetches Hydra’s public JWKS over verified TLS and checks its exact server identity. It no longer mounts a static JWKS file. Set the issuer and audience consistently in Hydra, Studio and Envoy. Envoy requires a valid signature, issuer, audience, expiration and not-before time and removes incoming identity headers before projecting verified claims. HTTP and WebSocket upgrades use the same public authentication boundary.

The generated keys use owner-only permissions. Set the proxy UID/GID to the file owner when starting Compose; the default container UID 1000 may differ from the host account. For repeated runs, save GALADRIL_PROXY_UID and GALADRIL_PROXY_GID in infrastructure/docker/.env.

Standalone proxy JWT fixture

From the repository root, initialize a unique signing key and public JWKS:

uv run infrastructure/envoy/tools/local_jwt.py init .local/jwt

The example uses PyJWT and cryptography; uv installs its declared dependencies in an isolated script environment. Initialization refuses to overwrite an existing directory. The private signing key stays under .local/jwt, outside every container mount. Only jwks.json is given to the standalone infrastructure/envoy/gateway.yaml profile at /etc/envoy/jwks.json. This offline profile is retained for isolated proxy tests. Compose and Kubernetes use Hydra and reject tokens from this unrelated fixture key. Do not use this example as the dashboard login flow.

Issue a 15-minute fixture token for an explicit subject and tenant. The request below targets a separately configured standalone proxy using that fixture JWKS:

umask 077
uv run infrastructure/envoy/tools/local_jwt.py token .local/jwt \
  --subject local-user --tenant tenant > .local/token.jwt
curl --cacert .local/identity/ca.pem \
  --header "Authorization: Bearer $(cat .local/token.jwt)" \
  --header 'Content-Type: application/json' \
  --data '{"query":"{ __typename }"}' https://localhost:8080/graphql

JWT verification establishes identity. Gateway still checks tenant and resource permissions through SpiceDB/Cedar; choose a subject with the required grants. Regenerate the token after expiry. Never deploy this local signer or copy its private key into Kubernetes. Use Vault-backed Kubernetes secrets for the deployed stack.

Compose and E2E parity

The pipeline E2E services inherit the shipped Compose definitions using native extends, including the single proxy image and bootstrap arguments. Fixture overrides select current application builds, isolated volumes, localhost ports, deterministic models and telemetry sampling. The E2E Registry administrative port remains protected by mTLS; application Registry calls use the local proxy listener. Public authentication and all normal internal API paths use Envoy.

Separate daemon-owned volumes keep server keys outside application, database and observability mounts. The proxy receives its configuration and server keys in one read-only volume, avoiding overlapping mounts under a read-only parent. The native merged Compose model verifies one proxy, shared namespaces, inherited hardening and absence of published application ports. PostgreSQL preserves its extension preloads and waits for its final TCP server. MinIO flushes individual Kafka notifications, Vision uses the native gRPC resolver, and Gateway waits for the canonical Zed schema job. E2E-only Ray settings remain fixtures.

The E2E fixture does not require volume subpath support; !override requires Compose 2.24.4+. CI and E2E use the official Compose 5.6.0 binary supplied by //infrastructure/docker:compose, pinned per platform with SHA-256 checksums. This keeps schema bootstrap dependencies independent of the executor’s installed Compose version. The merged-model regression checks every inherited application dependency, including Gateway’s successful SpiceDB schema installation. Use Compose 5.6.0 for the same deployment behavior locally. Registry remains at one replica until distributed branch locking supports concurrent writers.

Health, telemetry and rotation

Envoy checks Gateway/Scribe HTTP health and Registry’s gRPC health, rejects unhealthy upstreams, and bounds connections and pending requests. Administration and health listeners bind to shared loopback. Logs, traces and metrics use OTLP without credentials, bodies or query strings. Keep the OTLP collector available.

Rotate certificates before expiry and restart Envoy after replacing its static certificates, trust bundles or JWKS. Use overlapping public keys/trust roots when rotating. Ambient manages workload certificate rotation separately; its public TLS Secret and JWKS still require their own lifecycle.

Run bazel test //infrastructure/docker/tests/... //infrastructure/envoy/tests/... for native Compose contracts and actual Envoy validation. The single-proxy test covers public JWT/header integrity and the Registry, generation and tools paths. //tests/e2e:pipeline_lifecycle_test exercises the application pipeline with this same proxy; //infrastructure/kubernetes:ambient_test exercises actual mesh policies with echo API fixtures. See the deployment verification matrix for the scope and limitations of each suite.

Enterprise SSO

Galadril uses the free self-hosted Polis/Jackson and Hydra editions. No paid Polis portal or Ory Network subscription is required. Polis brokers OIDC and SAML2 and encrypts its PostgreSQL records with native AES-256-GCM. Hydra signs Galadril JWTs and stores clients and sessions, not users. iam_users remains the authoritative Galadril directory.

Organizations administer federation and permission imports through Gateway’s GraphQL API and the dashboard at /settings/sso. These operations derive the tenant from the authenticated JWT. Neither administrators nor automation pass a tenant identifier or edit routing tables manually.

Organization administration

Sign in, open your avatar menu and choose Administration. The landing page contains the organization name and links to People, Sign-in & security, and Permissions. The same destinations are available in the command bar to authorized administrators. People shows canonical accounts with their provider display metadata; email is never used to merge identities. Suspending a person retains their data and blocks subsequent authenticated HTTP requests. Role changes and account recovery require an explicit confirmation. Gateway refuses self-suspension and self-deletion, including attempts through the user upsert API. User state changes serialize per organization and recheck the active administrator inside the transaction. Since tenant management requires a direct SpiceDB administrator relationship, the surviving caller preserves administrative access even during concurrent mutual suspensions. Deletion disables the target before removing its authorization relationships.

To add a domain, follow Your domain → Your provider → Review: request its challenge, publish the returned _galadril.<domain> DNS TXT record and save the provider. Challenges expire after 24 hours. Gateway verifies the proof over authenticated HTTPS before reserving the domain or configuring Polis. Existing domains can rotate credentials without repeating DNS verification. Removing or replacing an issuer requires an explicit identity migration; updates preserve Polis IDs.

In Your provider, enter an HTTPS provider address or SAML metadata URL and choose Detect configuration. Gateway validates OIDC discovery or SAML2 metadata and checks the domain proof. The preview reports pending ownership verification separately; detection never reserves a domain or saves a connection. Choose Use detected settings to prefill the form, then review and save it. Client secrets remain write-only and cannot be discovered from public metadata. Discovery rejects private network addresses, follows no redirects, pins DNS answers, verifies TLS and limits response size and request duration.

OIDC configuration requires only the issuer and verified domain when the IdP supports Dynamic Client Registration. Gateway discovers /.well-known/openid-configuration, validates the exact issuer and public HTTPS endpoints, and optionally sends a write-only oidc_registration_token to the advertised registration endpoint. The registered callback is https://aeluin.gravitalia.com/api/oauth/oidc. If registration is unavailable, supply both oidc_client_id and oidc_client_secret. Empty credentials on an existing connection reuse its encrypted credentials. Discovery refreshes the upstream JWKS without manually copying public keys. The initial registration token is not retained. Enterprise client IDs cannot be rotated into a different Polis identity namespace through an ordinary credential update.

For SAML2, submit trusted saml_metadata XML instead of OIDC fields. The ACS is https://aeluin.gravitalia.com/api/oauth/saml and the audience is https://aeluin.gravitalia.com/sso. Signed metadata/certificate rotation is an administrator operation; OIDC .well-known does not replace SAML metadata. LDAP and Kerberos remain behind the enterprise IdP exposing OIDC or SAML2; Galadril never collects enterprise passwords.

Gateway exposes these GraphQL operations to both UI and automation, under the administration query or mutation field:

  • ssoSettings: secret-free settings for the current organization.
  • updateOrganization(name): changes its display name, preserving its identity.
  • users, roles, roleAssignments: authorized member and access listings.
  • updateUser(userId, isActive): suspends or restores an existing account.
  • setPasskeyMfa(enabled): changes the default-disabled MFA requirement.
  • resetUserPasskeys(userId): invalidates a member’s key and pending challenges.
  • requestSsoDomain(domain): returns a DNS ownership challenge.
  • detectSsoProvider(domain, address): previews validated provider metadata.
  • configureSsoConnection(configuration): creates or updates federation.
  • disableSsoConnection(domain): stops new logins while retaining identity links.
  • linkExternalIdentity(domain, externalSubject, userId): binds an immutable IdP subject to an existing active Galadril account without duplicating its roles.
  • setPermissionImport(enabled) and importPermissions(manifest).
  • configureRoleSync(configuration): approves explicit upstream-group mappings.
  • accessGraph(search, limit): returns authorized nodes and relationships.
  • setRoleParent, setResourceAccess: manage role inheritance and resource grants.
  • configureGeneralAccess(configuration): saves readable UTC access rules as Cedar.

Administrative writes require an active administrator and pass SpiceDB/Cedar authorization and append-only audit. Settings, provider previews, role mappings, access graphs and import results use typed GraphQL objects. Select only the fields needed by the caller; do not JSON-encode input objects or parse result strings. Provider previews expose an OIDC/SAML union. Secrets remain input-only.

users and roles return items and a nullable continuation after. The default page contains 20 results, with a maximum of 100. Pass the cursor with the same search to request more. Directory search folds case, accents and combining marks and tolerates misspellings in words of at least five characters. Delegated supervisors see only their authorized hierarchy. Send requests to /graphql using the HttpOnly session cookie and exact public Origin, or a valid Galadril access token in Authorization: Bearer .... Secrets are write-only, cleared from dashboard fields after submission, and stored only inside Polis’s encrypted database records. Gateway’s routing metadata and settings never contain enterprise secrets.

JIT account creation is opt-in (jit_provision, false by default). Prefer explicit account links for existing users. Identity keys are the tenant, connection and immutable upstream subject; email never merges accounts. Repeated and concurrent logins reuse the same account; disabled or deleted accounts cannot be recreated. New JIT accounts receive tenant membership, but no resource or administrative permissions merely by signing in.

Guided permissions

Open Permissions and choose Import automatically, Roles & people or General access rules. Each path provides a review before applying changes. Success and failure messages appear in place without reloading the dashboard.

Automatic import is off by default. Select an existing verified provider and explicitly map its group values to Galadril roles. Approved role names can be created automatically; unmapped provider values never create roles or confer access. The default claim path is raw.groups, matching Polis’s verified upstream userinfo; choose a different path only when your provider returns groups or roles elsewhere. Subsequent logins reconcile those imported assignments. Removing an upstream group revokes that provider’s assignment while retaining any manual assignment of the same role. Disabling synchronization leaves existing grants intact; revoke them explicitly if needed.

Roles & people provides search, assignment, role inheritance and an access graph. The graph includes authorized document grants and reports truncated results; refine the search to inspect a larger directory. Search text is limited to 128 bytes; directory selectors load 20 results at a time with Load more. Every continuation rechecks current permissions. Every role creation path shares an atomic quota of 256 names per organization, including retired names. Deleting a role therefore does not free its quota slot. This prevents repeated creation/deletion from bypassing abuse limits.

General access rules supports readable UTC time blocks or validated Cedar code, with a link to the Cedar documentation. Role selection uses canonical memberships rather than provider claims. Custom tenant Cedar restrictions exempt administrators so they can repair their configuration, while SpiceDB and tenant isolation still apply. Location rules are unavailable until a trusted geolocation source is configured; an IP address alone is not treated as verified country information.

An organization can store at most 128 Cedar policy identifiers, including inactive policies, with at most 8 KiB per policy. Named guided rules can coexist for different roles; review shows whether an existing identifier will be updated. Send one administrative write per GraphQL request; use the bounded import batch for ordered bulk changes rather than relying on nested field execution order.

Optional permission import

The organization’s administrator enables imports through administration { setPermissionImport(enabled: true) }. Automation uses the same administrator credential and authorization boundary. No global operator approval or SQL edit is needed. Imports remain disabled by default for every new organization.

      "kind": "role_assignment",

      "role": "analyst",

      "kind": "relationship",
      "resource": { "type": "group", "id": "research" },

The advanced editor accepts this import file format, then converts it to the PermissionManifestInput GraphQL contract. Each operation sets exactly one of roleAssignment, relationship or cedarPolicy; relationship objects use kind and id. Submit the object directly, with selected result fields:

mutation Import($manifest: PermissionManifestInput!) {
  administration {
    importPermissions(manifest: $manifest) {
      applied
      failedAt
      complete
    }
  }
}

The manifest contains local Galadril IDs and no tenant selector. The enterprise exporter maps its subjects and groups to existing Galadril users, roles and data-domain groups. Supported relationships are reader and ingester between groups and users; arbitrary SpiceDB schemas, usersets, cross-tenant identifiers and service principals are rejected. Cedar policies must pass Gateway’s native validator. SSO claims never enable imports or grant roles without an approved mapping.

Batches allow 64 operations, 128 KiB overall and 8 KiB per Cedar policy. Gateway validates the full manifest and all Cedar syntax before writes, then executes native IAM operations in order, with authorization and audit on each operation. It stops at the first error or denial and returns applied, failed_at and complete; earlier changes remain applied. This is not a transaction across PostgreSQL and SpiceDB. Retry idempotent operations after correcting the failure. Disabling imports does not revoke existing permissions; use enabled: false or policy active: false for explicit revocation.

Passkey second factor

An organization can require a passkey after either enterprise federation or a local Kratos password. This setting is off by default. Integration and lifecycle test fixtures explicitly enable it and use a software authenticator with real ES256 signatures; there is no bypass or test-account button in the dashboard. Hydra receives the completed login only after verification. Its access JWT contains acr=urn:galadril:webauthn:uv, mfa_generation and authentication methods. Galadril keeps the canonical IAM user; no extra user directory is introduced for WebAuthn.

SimpleWebAuthn validates the challenge, exact HTTPS origin, relying-party ID, signature, counter and required user verification. The relying-party ID comes from the hostname of AUTH_PUBLIC_ORIGIN, so configure that origin consistently and keep it stable across deployments. The first verified primary login enrolls one passkey if none exists; subsequent logins require that credential. Biometrics and device PINs remain on the authenticator. There is no password-only fallback when MFA is required.

administration { resetUserPasskeys(userId: "...") } is tenant-bound, authorized and audited. Verify the person’s identity using your organization’s recovery procedure before invoking it. The transaction increments their credential generation, removes the old key and invalidates pending challenges. Old JWT generations are rejected by Studio and Gateway; a fresh primary login then enrolls a replacement. HTTP requests and new WebSocket upgrades recheck account status and current MFA state. Existing WebSocket connections close at token expiry. Resetting another tenant’s key is not permitted.

Enabling Require a passkey for everyone immediately opens a blocking dialog for the administrator’s current session. Creating or verifying the key returns to the same page without reloading it. Other active sessions encounter the same gate when they next navigate or renew their token. A credential reset requires fresh primary authentication instead of allowing an invalidated token to enroll its own replacement.

Active dashboard sessions

The first-party Hydra client uses authorization code with PKCE and the refresh grant. The only supported automatic client migration upgrades the previous openid/authorization-code configuration; unexpected callback, audience or authentication changes are rejected. Refresh tokens remain encrypted inside a Secure, HttpOnly, host-only cookie and are never returned to browser JavaScript.

A visible tab active within the last five minutes checks its session once a minute. The server checks the current account and MFA policy on every check and rotates tokens near expiry. A 30-minute idle timeout and an eight-hour absolute lifetime still require a new sign-in. Browser tabs serialize renewal when the Web Locks API is available. Temporary service failures display an in-place connection message and retain the page; invalid sessions require sign-in, and new passkey requirements open the dialog. Logout revokes the refresh token.

Kubernetes and k3s with Istio Ambient

Docker Compose uses one shared local Envoy and remains the lighter deployment option. Its application namespace is one trust domain. Kubernetes runs the five application workloads without Envoy sidecars. Istio installs one ztunnel per node, one shared api-waypoint for HTTP/gRPC policy, and a public ingress that terminates TLS and validates JWTs. Applications use Service DNS and explicitly select ambient proxy mode; the default mode still requires loopback.

The manifests use native Kustomize and the upstream Istio Helm charts. The validated versions are Istio 1.31.1, Gateway API 1.6.3, and k3s 1.37.1. Use a Kubernetes release in Istio’s supported range. K3s runs on Linux; on macOS, k3d runs it inside Docker’s Linux VM. Adding Istio also adds its control plane, CNI agent, node tunnel and shared proxies. Compose therefore remains the smaller option for a Mac. Vision’s embedded Ray runtime has a separate memory requirement; replacing Kubernetes with k3s does not reduce the application’s model or worker memory.

Enforcement and observability

Ingress exposes only /graphql, removes caller-supplied identity headers, and uses Envoy’s native JWT verification with mandatory expiration and zero clock skew. Missing or rejected identity returns 401 or 403 at ingress. Gateway retains tenant, resource and generation-capability authorization. TLS 1.3 is required on ingress and mesh connections.

Namespace enrollment uses a waypoint for both Service and Pod destinations. The waypoint policy targets its Gateway and matches destination port, source ServiceAccount, method and exact API path, including the Registry RPC allowlists. This also protects direct Pod IP calls. Destination ztunnel policies accept only the waypoint’s identity; PeerAuthentication requires strict mTLS. The original caller is checked at the waypoint, before that final hop. Node readiness probes are a Kubernetes administrative path, not public routes.

Application telemetry uses OTLP. Istio’s tracing and access logs use the otlp and otlp-logs providers configured for otel-collector.observability.svc.cluster.local:4317. Ensure the collector exists and enroll its namespace or secure its transport. Collect native Istio/ztunnel Prometheus metrics through the OpenTelemetry Collector’s Prometheus receiver, then export through the existing metrics pipeline. Do not include credentials, query strings or bodies in access log formats. Workload certificates rotate through Istio; the public TLS Secret and public JWKS have separate rotation.

Email accounts with the official utils plugin

The utils email service collects multiple IMAP mailboxes, stores mail durably, delivers opted-in messages and attachments through native ingestion, and prepares or sends replies through verified TLS SMTP. Google and Microsoft accounts use OAuth consent with IMAP/SMTP; other providers use passwords or app passwords. Providers must enable these protocols. Gmail REST history and Microsoft Graph delta synchronization are not adapters in this version.

Open User settings → Email (/settings/user#email). The former /settings/email address redirects there. OAuth (/settings/user#oauth) contains personal service connections. Choose a row in the email account list to open its Connection, Messages or Replies panel. The account’s action menu groups connection tests, editing, access grants and deletion. Each connection has its own folders, collection interval, ingestion choice, response profile and access grants. On first collection, the default is new messages only. Choose all available messages to import history; review automation settings before doing so. Collection uses read-only IMAP and does not mark messages as read. Local category labels organize the collected copy; they do not modify provider folders or flags. Removing a connection removes its local mail, drafts and tokens, without deleting messages at the provider.

Sending without IMAP

The IMAP server is optional. Leave it empty in the server-settings step for an outbound-only connection, such as SMTP2GO. No separate mode switch is needed. Galadril tests SMTP authentication, retains the connection in Pengolo’s sender selector, and keeps the same approval and duplicate-delivery protections. It does not poll the connection, display receiving controls or ingest messages.

SMTP supports STARTTLS on ports 25, 80, 587, 2525 and 8025, and implicit TLS on 465, 8465 and 443. TLS and certificate verification are mandatory on every port; credentials are never sent before the secure channel succeeds. For SMTP2GO, mail-eu.smtp2go.com:2525 uses STARTTLS; enter the SMTP user credentials and a verified sender address from your SMTP2GO account, following the provider’s SMTP relay instructions. Server probing sends no credentials or email.

Detect servers from a domain

For a new connection, enter only the email address and select Continue. The wizard discovers secure servers before asking for credentials. If discovery is incomplete, it opens the server-settings step; detected settings can also be edited explicitly. Editing an existing connection retains its advanced form.

The worker first queries _imaps._tcp, _submissions._tcp and _submission._tcp DNS SRV records following RFC 6186 and RFC 8314. Missing services fall back to Mozilla’s public ISPDB, the domain’s HTTPS Autoconfig endpoint and /.well-known/autoconfig/mail/config-v1.1.xml. One parent-domain HTTPS Autoconfig endpoint is also checked for subdomains. For example, student addresses at etu.univ-lorraine.fr can use autoconfig.univ-lorraine.fr.

Only the domain is used. Provider templates receive the synthetic address discovery@<domain>, never the user’s mailbox name. XML must explicitly match the requested domain and declare IMAP 993 with TLS and SMTP 465 with TLS or 587 with STARTTLS. Documents are bounded to 64 KiB; document types, redirects, unverified certificates and plaintext HTTP fallback are rejected. HTTPS connections pin validated public addresses and do not use environment proxies. A bad certificate on one candidate does not prevent trying another verified candidate.

DNS answers and successful public configurations are cached with bounded sizes. Discovery has a total deadline, bounded concurrency and record counts. Endpoints are validated against the operator network policy, and actual mail connections revalidate and pin addresses and verify TLS certificates. No credentials are read or sent and no account is saved during discovery. Discovery is authenticated and unavailable to delegated model tool calls. MX records are not substitutes for IMAP access or SMTP submission records. JMAP is not an adapter in this version.

Gmail server detection works independently of application registration. The wizard offers OAuth only when the operator has configured a Google client. With no client, it goes directly to the sign-in step and requests an app password. A regular Google account password is not the app password. Availability depends on the account’s Google security and organization policies. University templates with no username rule ask for the institution’s login identifier explicitly. Changing an existing connection’s host still requires replacement credentials.

Resolve recipients from an address book

Pengolo can search a connected Zimbra account’s personal contacts and organization directory before preparing an email. University of Lorraine student and staff domains have maintained HTTPS bindings. Other Zimbra deployments can configure UTILS_ZIMBRA_DIRECTORIES on the email worker as a JSON map of exact email domains to trusted Zimbra hostnames, for example {"example.org":"mail.example.org"}. Only the fixed HTTPS /service/soap endpoint is used, with verified certificates, public-address validation and DNS pinning. Credentials never enter the model.

Lookup requires the connection’s read permission. It uses a bounded live autocomplete query, including the global address list, rather than copying the organization directory. Password-authenticated Zimbra accounts are supported; Google/Microsoft OAuth accounts do not gain a Zimbra adapter. Up to eight readable accounts are queried and at most twenty deduplicated individual contacts are returned. Sender account addresses are withheld. Incomplete searches and multiple matches require clarification through Pengolo’s question card before a draft is created. The user still chooses a sending account and approves delivery.

Replies and automation

Select any configured Scribe model alias, local or API-backed. If it becomes unavailable, Scribe automatically tries up to three configured models supporting the same reasoning options, preferring the same provider. If its configuration has been removed, the configured default supplies the compatibility baseline. With no usable configured model, generation fails without sending. Registered Skills have searchable names and descriptions; language is searchable too. Instructions, tone and a Markdown or HTML signature are configurable. Single line breaks are preserved; <small> is supported for smaller mentions. Signatures are sanitized and appended after generation, with a plain-text alternative. Metadata fields are substituted after Markdown rendering, preventing them from introducing links or images through Markdown syntax. Images require HTTPS URLs without credentials, IP literals, local hostnames or nonstandard ports. The service never fetches them. The isolated preview blocks image loading until the viewer selects Show external images; recipients retain their mail client image-loading policy. Scripts, frames, styles and inline data images are removed. Selecting an API model sends the email context to that model’s provider under the existing Scribe configuration.

The three modes are:

  1. Generate on demand: collection does not call a model. Generate from a selected message or compose manually.
  2. Prepare drafts for approval: collection generates categorized drafts. A user with approve reviews the exact revision; send is separate.
  3. Automatic replies: requires automate, exact allowed sender addresses, and a global rolling 24-hour maximum (1–100, default 10). Optionally set a per-sender rolling 24-hour maximum or one acknowledgment per conversation. There is no fixed one-reply-per-sender rule. Conversation identity follows References / In-Reply-To, independently of the sender.

Every edit to a draft clears approval. Updating connection settings also clears existing approvals. Automatic replies keep the original sender as the only recipient and do not send attachments. Automated messages, mailing lists, delivery reports and messages not addressed to this mailbox require review. Permanent source deduplication prevents replies to the same message twice. Email-supplied instructions cannot grant tools, credentials or send authority.

The optional utils.mcp.email Scribe toolset reads authorized mail, searches it, classifies it and saves drafts through the existing delegated conversation lease. It cannot reveal credentials, configure accounts, approve or send. utils.skill.email supplies the corresponding packaged correspondence Skill. Registered plugin Skills also appear as read-only specialists in Pengolo; selection and custom-specialist management use separate views.

The native propose_email tool only prepares a durable, editable card containing To/Cc/Bcc, subject and body. It receives no sender account or credentials and cannot approve or send. Clicking Send resolves the current user’s authorized accounts in the interface. One usable account is selected automatically; multiple accounts require an explicit choice. The worker still checks approval, send rights and the exact draft revision. Bcc addresses are envelope recipients only. The proposal identifier survives reloads, so reopening a sent card cannot resend it.

New response profiles start with an empty signature. An optional Ref. : <code>{{ ref }}</code> field can be added explicitly. Signature fields are substituted at sending time, never evaluated as code. The preview uses example values. Existing custom signatures remain unchanged.

FieldValue

Incoming messages receive a tenant/account-scoped reference derived from their durable identity. Recollection and replay preserve it. Generated replies retain the source reference, as do manual replies whose source identity is verified. Standalone drafts receive their own reference, preserved through edits. It is included in the ingestion envelope metadata and the X-Galadril-Reference outgoing header, allowing collection, downstream analysis and replies to be correlated. References convey no access rights. Template values are HTML-escaped before sanitization, and expansion is bounded to 64 KiB.

SMTP cannot guarantee exactly-once delivery across a lost acknowledgment. Some providers accept an email address for IMAP but require a separate account login for SMTP. Use the login supplied by the provider’s autoconfiguration or mail-client settings; an IMAP authentication success alone does not verify SMTP. Before contacting SMTP, the service durably claims the approved draft. A crash or uncertain response leaves sending or uncertain, blocking blind retries. Check provider logs or Sent mail using the displayed stable Message-ID before deciding whether to compose another message. There is no automatic resend or delivery reconciliation mutation in this version.

Correspondence identity

Correspondence is linked from the RFC Message-ID, In-Reply-To and References headers. The thread identifier is its root Message-ID. A durable number identifies each distinct message in that thread; importing it again or collecting an email sent to the same mailbox reuses that number. The optional signature reference is <root-message-id>/number. Removing it from the body does not break the links. Collected messages can be searched by their Message-ID or thread identifier.

The Messages card opens a graph of the thread, recorded Scribe analyses, ingestion receipts and up to 100 recent pipeline executions visible to the user. A source link uses native ingestion metadata, never arbitrary text inside a message. The graph contains up to 128 messages; legacy correspondence is indexed in bounded batches. Original GDR- references remain in internal metadata for compatibility with already ingested records.

Optional opening signals

Opening tracking is off by default. A user may enable it on an individual draft or in their reply profile. That choice is part of the approved draft revision; changing it requires approval again. Scribe can propose content but cannot enable tracking or read opening signals through delegated tools.

The optional utils Rust service tracker serves only /healthz and GET /email/open/<opaque>.gif. It returns the same transparent GIF for valid and unknown tokens. Its dedicated capture key can only submit opening signals to the private worker; it has no mailbox database, account keyring or service credential. It bounds concurrent forwarding to 32 requests with a three-second deadline and exports aggregate outcomes through OTLP without IPs, tokens or request URLs.

Leave the public origin empty when tracking is unconfigured. Before enabling it on real mail, request a test pixel through the public hostname and verify an opening signal on an explicitly opted-in test delivery. A successful private health check alone does not prove tunnel or DNS reachability.

The Opening signals action on a tracked delivery lists timestamps and observed IP addresses. Each image request is a signal, not proof that a person read the email: image blocking can hide opens, while privacy proxies and security scanners can produce or consolidate requests. Multiple recipients share the delivery’s pixel, so an event cannot identify which recipient opened it. History is delivered in pages of 25, capped at 1,000 signals per delivery and purged after 90 days. Pixel requests contain no sender, recipient, tenant or document reference. Application traces use a fixed route label rather than the opaque token.

Ingestion and pipeline routing

Ingestion is opt-in per connection. Provision a service identity restricted to the intended tenant and input group, then mount its renewable bearer-token file. The JSON at UTILS_INGESTION_FILE maps each tenant ID to settings and token_file. Settings are gateway_url (authenticated public /graphql), storage_origins (exact allowlisted origins), tenant_id, subject, group_id and optional SDK bounds. Map key and tenant_id must match. The service rereads the token file for each mutation; external rotation can replace it atomically.

Use the SDK’s native staging/upload/finalization delegation. Attachments are committed before their email envelope, and ingestion checkpoints advance only after finalization. Redelivery can happen after an uncertain failure; downstream processing should deduplicate the stable source name/message identity. Once ingested, data access follows the destination’s native ingestion/group policy, so choose that group deliberately. Account credential grants are never copied to ingested documents.

Add the Email accounts plugin input (utils.input.email) to the pipeline. It uses schemas/avro/email.avsc, source_kind: email, the configured group and a stable email JSON filename pattern. Native regex, metadata and Scribe routing can inspect record.raw_payload.content and metadata fields such as record.raw_payload.metadata.subject, sender, date, account_id and thread_id. Native branch routing continues to enforce linked-pipeline permissions, cycles and composition limits.

Durability and operations

SQLite uses WAL, foreign keys, full synchronous commits and a process lock. Run one worker per database on persistent local storage. Back up the database with a consistent SQLite backup mechanism, together with all retained keyring versions; copying only the live main file can miss WAL transactions. Credentials, message content, drafts, response profiles and pending OAuth payloads are AES-256-GCM encrypted with tenant/account/purpose binding. Basic connection metadata, ACLs, cursor/status and audit metadata are intentionally queryable. Do not delete old key versions while encrypted rows or backups still use them.

Collection resumes from UIDVALIDITY/UID checkpoints. Remote message size is bounded before allocation; collection, MIME parts, lists and outgoing attachments are bounded. One poll fetches at most 25 messages per folder, searching bounded UID windows; large historical imports progress over multiple polls. The default poll interval is 120 seconds. List previews omit attachment contents and truncate bodies; explicit message/draft reads return the full bounded content.

OTLP reports operation outcomes and worker lifecycle without mail text, prompts, passwords, refresh tokens or exception payloads. Audit events record the actor, connection, action and time. needs_attention means a provider, authorization, model or ingestion operation needs operator/user review; successful earlier checkpoints remain durable. Calendar/contact adapters and provider-side move/archive/delete operations are separate future capabilities.

Manual server settings accept DNS hostnames rather than web URLs. Before moving to sign-in, the worker verifies public/policy-approved addresses, pins them and checks certificate-verified IMAP TLS and SMTP TLS/STARTTLS without credentials. The browser validates syntax, while actual socket checks run on the worker. Returning from sign-in restores manual server settings when they were entered; automatically discovered settings can skip that step.

Internal Architecture

Galadril is divided into three distinct operational layers (Medaillon architecture):

  1. The Synapse: MinIO (S3) and Redpanda (Kafka).
  2. The Ingestor: A Rust service that catches raw data and normalizes it.
  3. The Vision: A Python service that applies AI models and extracts insights.

Authorization, tenant isolation, and lineage

Previous model and threats

Gateway verified JWTs and usually checked Loth, but WebSockets used hard-coded identities and permission strings had no repository contract. Intake accepted mutable tags, fell back to a tenant parsed from an object key, and preserved a payload-supplied authz object. Vision trusted Kafka tenant fields and could materialize arbitrary relationships. Database provisioning did not enable RLS; Gateway’s tenant transaction set search_path but not app.tenant_id; and background causal/cache paths omitted tenant identity.

Those gaps enabled forged tenants, BOLA/IDOR, confused-deputy processing, cross-tenant cache/graph access, permission drift, and RLS bypass.

Invariant and trust boundaries

Authentication identifies the actor; trusted claims resolve the tenant; SpiceDB authorizes a domain permission; Cedar may further deny using trusted context. PostgreSQL RLS limits operational row access. Registry isolates versioned ontology and pipeline artifacts by tenant and resolves its internal lakeFS repository mapping server-side. See versioned storage.

External users write only to staging with a short-lived URL. Gateway checks tenant:ingest, copies into the tenant prefix, and replaces security metadata. Destination-bucket IAM must allow writes only from Gateway. Intake accepts only object-store notifications on an ACL-protected topic, requires Gateway-authored scoped metadata, overwrites document authz, and publishes on topics whose only producer is Intake. Vision rejects missing/mismatched context and materializes only owner-approved relationship categories.

Intake has no public HTTP policy surface: its ingress is the object-store notification topic. That is still a security boundary. Only the object store may publish notifications, and only Gateway may write the destination bucket.

Kafka ACLs, destination-bucket IAM, mTLS/service authentication, and distinct SpiceDB tokens are part of the boundary. X-Internal-* headers are not trusted.

Security context and execution identity

Protected work carries request/trace ID, normalized tenant, actor type/ID, authentication issuer, execution kind (user_delegated or service), target, permission, optional ZedToken, and origin/delegation. User metadata is separate and cannot overwrite this context.

Async work records the initiator even under a service execution identity. Revocable or destructive work re-checks permission at execution; historical allow flags are invalid. Tenant is part of cache, idempotency, graph, and deduplication keys.

PostgreSQL and SpiceDB lifecycle

There is no cross-system transaction. Vision persists tenant data plus an idempotent authorization-outbox row atomically. Vision owns delivery and reconciliation. New resources stay non-addressable until authorization exists. Deletion removes external access first, then data, with a reconciliation tombstone for partial failure.

Normal services use non-owner, non-superuser, non-BYPASSRLS roles. Reconciliation and maintenance use separate identities and entry points. SET LOCAL app.tenant_id immediately follows BEGIN; missing context denies, and transaction end clears state before pool reuse.

Gateway uses one DATABASE_URL, verifies the normal role and every tenant table’s forced RLS at startup, and refuses unsafe configuration. Vision uses user/password for tenant work and requires separate maintenance_user/maintenance_password for schema or authorization-outbox reconciliation. Production secrets must not reuse the development credentials in infrastructure/docker/connectors.yaml.

Arbitrary permission-record mutations do not exist. New grants must target a typed resource relation owned by one service.

Contextual Cedar restrictions

Tenant administrators can install syntax-validated Cedar policies through administration { setCedarPolicy(...) } or the guided configureGeneralAccess mutation. Cedar runs only after SpiceDB allows. Role membership comes from the tenant’s canonical IAM directory and hour values come from the server’s UTC clock. Provider role claims and caller-supplied clock values cannot substitute for those facts. Region and device posture require a separately trusted issuer mapping; arbitrary request headers are never accepted. The example in schemas/spicedb/examples/contextual-constraints.cedar shows a time, region and device restriction. Geography-based blocks remain unavailable in the dashboard until a trusted IP geolocation source is configured.

Tenant custom policies exempt verified administrators after the structural permission check so an invalid or overly strict policy cannot prevent repair. The exemption never grants a resource denied by SpiceDB or another tenant’s resources. Every check reads the current policy source from PostgreSQL; the local cache reuses only identical compiled policy text. It retains at most 64 tenants and 8 MiB of source text, evicting the oldest retained tenant when either budget is reached. Compiled Cedar structures and in-flight checks require additional memory. A policy update therefore applies across Gateway replicas without waiting for a local cache invalidation.

Audit

Emit authorization.check, authorization.relationship.write, security.context.accepted, security.context.rejected, and tenant.transaction. Include request/trace, tenant, actor/service identity, resource, permission, decision, consistency, relationship operation, and ZedToken when available. Never include bodies, prompts, credentials, tokens, or arbitrary payload metadata. Security audit storage is access-controlled and retention-managed independently from debug logs.

Required loth changes

The pinned interface needs per-check consistency (minimize_latency, at_least_as_fresh, fully_consistent), checked_at in check results, written_at in relationship acknowledgements, and a hard SpiceDB-AND-Cedar invariant. Local Gateway code evaluates Cedar only after a SpiceDB allow until that interface is available.

Gateway membership writes await Loth’s native SpiceDB write acknowledgement. Revocations therefore complete in SpiceDB before removing PostgreSQL approval; enabling writes follow a durable PostgreSQL commit. A crash between those separate operations can still leave approved access unavailable. A durable Gateway outbox and reconciliation, with written_at acknowledgements, remain required before claiming crash-atomic PostgreSQL/SpiceDB lifecycle convergence for IAM administration.

Developer guide

  1. Add the permission to schemas/spicedb/schema.zed and document semantics and its sole relationship writer.
  2. Add a typed application permission; never add a raw string check.
  3. Resolve tenant from trusted authentication/delegation and require a tenant-qualified target ID.
  4. Check SpiceDB before side effects; apply Cedar only as a restriction; fail closed on denial, timeout, malformed context, or policy errors.
  5. Use a tenant transaction for SQL. Add RLS USING and WITH CHECK, force RLS, and test two tenants, missing context, and pool reuse.
  6. For dual writes, choose one relationship owner, use an outbox/compensation, make writes idempotent, and define reconciliation plus ZedToken semantics.
  7. For background work, carry initiating and execution identities, bind tenant into ACLs/idempotency keys, and state whether execution re-authorizes.
  8. Add positive/negative SpiceDB behavior tests, forged/missing/cross-tenant tests, dependency-failure tests, and structured audit assertions.

Deterministic security tests

Run the complete deterministic suite with:

bazel test //platform/vision/tests/security:authorization_defense_in_depth

The suite uses fixed-version Postgres, SpiceDB, and Kafka images. Gateway tests install the current schema into a real Postgres instance, then prove concurrent tenant transactions cannot observe each other, pool reuse clears SET LOCAL, forged writes fail, missing context sees no protected rows, and explicit system queries remain usable while tenant transactions are active. SpiceDB tests load the canonical schema, exercise permissions rather than relationship internals, and verify immediate revocation and cross-tenant denial. Kafka tests send valid and forged security envelopes through a real broker into Vision’s production normalizer. Intake unit and integration tests independently reject every missing, forged, or mismatched security-context field.

All fixtures use fixed IDs and bounded readiness checks. Each container has a fresh datastore; no test depends on execution order or external state.

A literal process-level Intake -> Vision model -> Gateway test is not currently possible under the three-container constraint. Intake production ingress also requires S3 notifications and Schema Registry, while Vision model execution requires Ray and model artifacts; there is no repository adapter that connects the three service binaries in-process. The deterministic suite therefore tests each real security boundary without mocking Postgres, SpiceDB, or Kafka. To add the literal pipeline test, first introduce narrow injectable adapters for the object notification/schema lookup and model executor, then drive the same signed fixture through all three services. Do not add more infrastructure to this suite merely to simulate those boundaries.

Enterprise authentication

Tenant-owned administration contract

Gateway manages verified email domains, SSO connections, identity enrollment and permission import settings. Administrative inputs never select another tenant: Gateway derives the organization from the authenticated principal. Tenant administrators and authorized automation use the same authorization and audit boundary. Permission imports are disabled by default and executed by Gateway, not Studio.

A trusted deployment provisioning process initializes an organization and its first administrator through an API, without SQL or manual tenant identifiers. Its credential cannot update existing organizations. Subsequent management uses tenant administrator permissions. Additional email domains require DNS TXT ownership verification. Unknown email domains never cause anonymous organization creation.

Polis owns SSO secrets and encrypts PostgreSQL records with its native AES-256-GCM store. Gateway stores only connection references and routing metadata. Secrets are write-only inputs and never appear in management queries or audit details. Hydra owns signing keys and OAuth client credential hashes. OIDC discovery and remote JWKS replace copied public keys. Upstream client registration depends on the enterprise IdP; confidential-client credentials can be entered securely through Gateway when registration is unavailable.

This contract separates enterprise identity federation from Galadril resource authorization. Polis handles upstream SAML2 and OIDC connections. Hydra is the only issuer of Galadril API access tokens. Studio’s server implements the login and consent bridge; its browser code never receives an OAuth client secret or a refresh token. Gateway and Registry receive no issuer signing keys.

Studio has no database driver, database credential, SQL, or migration ownership. Its server retains HTTP cookies, CSRF checks and OAuth navigation. Canonical identity resolution and all passkey persistence go through Gateway’s private GraphQL schema at /internal/auth/graphql. This schema uses a separate service credential, is absent from public ingress, and preserves transaction-local RLS, one-time challenges, counter preconditions and reset generations in Gateway.

Nuxt’s framework telemetry is disabled. Browser code exports no telemetry. Server metric export is disabled by default and can export only aggregated authentication counts with bounded operation/outcome labels. It exports no traces, logs, request bodies, identities, tenant identifiers or host/process resource attributes.

Identity and tenant binding

An administrator registers an exact, verified email domain against a Galadril tenant and a Polis connection. Domains select a connection; they never prove identity or membership. A domain has exactly one owner and cannot silently choose between tenants. Connection administration is private and separate from the unauthenticated discovery endpoint.

The authenticated principal is identified by the tuple (tenant, connection, external subject). Email addresses are mutable display attributes and must not link accounts. The callback verifies the selected connection’s OAuth transaction before resolving this tuple to an immutable Galadril user ID. Disabled or deleted users cannot authenticate or be recreated by just-in-time provisioning. Provisioning requires an explicitly enabled connection policy. Authentication projects the canonical tenant membership into SpiceDB; it does not grant a document, a role or an administrative permission by itself.

Hydra has no user directory. External accounts map to iam_users; several administrator-approved identities may reference one existing account without duplicating its roles. Permission import is a separate, default-disabled tenant option. A bounded manifest goes through Gateway’s existing administrative mutations and audit, using the caller’s verified JWT. Only compatible Cedar policies, role assignments, and supported data-domain relationships are imported. An administrator can separately approve a connection-specific mapping from selected upstream groups to Galadril role names. Approved names may be created automatically within the same tenant quota as manually created roles. Unmapped claims cannot enable imports, create roles or grant permissions. Imported assignments retain their provenance so a later login can revoke an upstream assignment without removing a separately maintained manual assignment.

The optional local Compose profile uses Kratos for test credentials. Its immutable identity ID binds explicitly to an existing IAM account; administrator-only Kratos metadata carries canonical references, which Studio checks against the tenant’s active IAM binding. Public session responses and editable traits cannot establish that binding. Gateway’s deployment-authenticated local enrollment creates the first test administrator automatically. Public registration remains disabled. Local accounts use the same Hydra issuer and authorization boundary as enterprise accounts, and logout revokes their Kratos session as well as Galadril cookies.

Tokens and sessions

Optional passkey second factor

Each organization can require a Galadril WebAuthn second factor after either Polis federation or Kratos password authentication. The policy is disabled by default; authentication fixtures explicitly enable it. No Hydra login grant or Galadril access token is issued until the second factor succeeds. An account without a credential enrolls one during this authenticated transaction. Passkeys reference the existing canonical IAM user; this introduces no user directory.

Registration and assertions require user verification, the configured HTTPS origin and its RP ID. Short-lived challenges are bound to the browser transaction, tenant, user and reset generation and consumed once, including failed attempts. Only public credential material is persisted under tenant RLS. Concurrent enrollment, challenge replay and reset races fail closed.

Gateway exposes tenant-authorized, audited policy and credential reset mutations. A reset deletes public credentials, invalidates pending challenges and advances the user’s generation atomically. The next successful primary authentication requires enrollment again. Credentials cannot be reset through email recovery or an unauthenticated endpoint. Gateway and Studio reject tokens whose second-factor generation no longer satisfies an enabled policy. Enabling the policy on an existing dashboard session opens a blocking passkey dialog immediately. An authenticated OAuth step-up issues a replacement token after enrollment or verification, preserving the current page. A token invalidated by an administrator’s credential reset cannot use this shortcut: fresh primary authentication is required before reenrollment.

Hydra issues short-lived asymmetric JWT access tokens with issuer, audience galadril, Galadril sub, tenant_id, iat, nbf and exp. Optional role, region and device_trust claims require a separate trusted mapping; arbitrary upstream groups and request parameters cannot set them. ID tokens are never accepted as API credentials. The first-party dashboard uses authorization code with S256 PKCE, state and nonce, and requests openid offline_access. Refresh tokens stay in an encrypted, host-only, Secure, HttpOnly cookie. Recently active, visible tabs periodically contact the same-origin refresh route. That route rechecks the active account, tenant binding and current passkey generation even when no token rotation is necessary. Near expiry it exchanges the refresh token, verifies the new access token and stores the rotated refresh token. Sessions have a 30-minute idle timeout and an eight-hour absolute lifetime; hidden or inactive tabs do not keep extending them.

The access token cookie is host-only, Secure, HttpOnly, SameSite=Lax and scoped to /. Studio verifies its signature, issuer, audience, token purpose, expiry and tenant binding before serving authenticated routes. Unsafe cookie-authenticated requests require the exact public Origin; WebSocket upgrades enforce Origin as well. Login transactions are bound to a short-lived encrypted browser cookie. Logout revokes the refresh token, clears session and transaction cookies, and prevents Hydra session reuse.

Organization access administration

Public GraphQL management operations live under administration in both the query and mutation roots. They derive the tenant from the verified principal. Directory searches and the access graph have bounded results, and searches are filtered to the caller’s own roles and subordinate roles. Administrators can manage their organization’s directory; nonadministrators cannot use directory queries to enumerate unrelated members or roles.

The permissions interface separates approved enterprise mappings, role and resource relationships, and general access rules. Role inheritance uses native SpiceDB role#member usersets. Graph results expose only authorized tenant relationships and explicitly report truncation. Role creation reserves a name atomically against a lifetime quota of 256 names, including retired names, so automatic creation and create/delete loops cannot bypass abuse limits.

General rules compile to native Cedar policies using authoritative role membership and server UTC time. Custom tenant Cedar rules do not restrict administrators, preserving their ability to repair a policy. This exemption occurs only after SpiceDB allows the structural action; it never bypasses tenant isolation or grants document access. Location rules remain unavailable until a deployment provides a trusted geolocation source. Browser-supplied locations and arbitrary JWT role claims cannot establish those attributes.

Proxy and workload trust

The public Envoy exposes the dashboard, required Polis callback endpoints, Hydra’s authorization/discovery endpoints and authenticated /graphql. Provider admin, introspection and database endpoints are never publicly routed. Initial enrollment uses a dedicated credential on /provisioning/organizations; tenant management uses the authenticated Gateway API. Identity headers are removed before JWT validation. Envoy projects only verified claims and strips credentials before forwarding to Gateway. Expiry is enforced after signature verification using the projected exp claim; Envoy’s default clock tolerance cannot extend the token’s API lifetime.

JWKS locations are deployment configuration, never JWT jku or browser input. Remote keys use an authenticated TLS upstream (Compose) or authenticated Ambient workload transport (Kubernetes). Public discovery advertises the canonical issuer and HTTPS JWKS URI. Fetches have bounded timeouts and caches; no local fallback accepts an unverified key. Rotation retains old verification keys until all issued tokens expire. Gateway retains its active-user, SpiceDB, Cedar and RLS checks. Registry retains its workload/RPC allowlists and receives no public login route.

Authentication emits bounded OTLP events and counters. Never record emails, authorization codes, cookies, tokens, client secrets, or callback query strings.

Enterprise protocols

Polis directly brokers OIDC and SAML2. LDAP and Kerberos are supported through an enterprise IdP exposing OIDC/SAML; Polis is not a native LDAP or Kerberos server. An optional LDAP-to-OIDC connector can be deployed separately when the enterprise has no existing IdP. Galadril must not collect enterprise passwords.

Proxy trust boundary

Docker Compose uses one Envoy for local development. Application listeners bind to loopback in its shared network namespace; all local applications belong to one trust domain. This protects the public API but does not isolate compromised workloads from each other’s loopback ports. The production Ambient deployment uses transparent interception, workload identities and a required shared waypoint. A Docker bridge, cluster network, source IP or tenant identifier is never proof of identity.

The public Gateway listener requires TLS and a JWT with a valid signature, issuer, audience, expiry and not-before time. Envoy removes incoming identity headers before validation and projects verified claims into reserved headers. Gateway accepts exactly one value for each mandatory claim, validates tenant syntax, and rejects expired identities. HTTP and WebSocket upgrades share this boundary; WebSocket connections terminate at token expiry.

Ambient authenticates internal API connections through ztunnel mTLS and workload identities issued by Istio. Transport policies require an explicitly permitted ServiceAccount identity; waypoint policies restrict API routes. Registry readers cannot call mutation RPCs. Gateway can mutate Registry state; Scribe can call only the delegated tool endpoint, and only Gateway can start Scribe runs. The delegated generation capability remains a resource authorization credential and expires independently of workload authentication.

An authenticated workload does not acquire tenant or object permissions. Gateway retains SpiceDB, Cedar, PostgreSQL RLS and audit checks. Registry trusts Gateway’s authorized mutation requests; Intake and Vision receive read-only runtime access in Ambient. There, compromise of a workload grants at most its explicitly allowed transport routes. Protect pod execution, deployment configuration, certificate issuance and secret storage as part of the trusted computing base.

Readiness reflects the application listener, including successful startup of its required dependencies. Envoy checks Gateway/Scribe health and Registry’s gRPC health service, rejects unhealthy upstreams, bounds connections, and exports traces and access decisions over OTLP without credentials or payloads. Envoy administration is local. The dedicated health port exposes no API route and is excluded from published Services. Kubernetes uses native application probes and keeps health routes out of the public ingress. The public route exposes only /graphql.

Certificate chain and SAN verification establish transport identity and message integrity. They do not attest the running binary or host. Signed image admission, image digests, trusted nodes and, when required, hardware-backed attestation must be enforced by the orchestrator. Static bootstrap files require an explicit proxy restart for JWKS/trust changes; production PKI rotation must reload them before expiry or replace static secrets with SDS.

This boundary covers Gateway, Registry, Scribe and their API callers. Kafka, PostgreSQL, S3, lakeFS, SpiceDB, model providers and OTLP have their own connector credentials and transport configuration. Their sample Compose transports remain development-only; a production rollout also requires TLS and narrowly scoped accounts for each of those dependencies.

Kubernetes without sidecars

The Kubernetes and k3s deployment uses a managed mesh without application sidecars. Istio Ambient separates the node-level mTLS tunnel (ztunnel) from shared Envoy waypoint proxies that enforce HTTP/gRPC policies. Workload identity remains distinct per service; sharing a proxy must not replace it with a common node certificate or source IP. JWT validation, trusted claim projection and RPC allowlists require the L7 waypoint or ingress layer. The L4 tunnel alone cannot enforce those policies.

The Ambient profile replaces loopback egress addresses with Service DNS, makes application listeners reachable through the mesh, and enforces strict mTLS and the required waypoint on every protected path. Direct Pod IP access and ingress traffic must not bypass JWT or RPC checks. Gateway may trust projected identity headers only when the mesh authenticates and restricts their supplying proxy. The source-workload policy belongs at the waypoint; destination tunnel policy must admit that waypoint, whose identity replaces the original caller on the final hop. Separate ServiceAccounts preserve each service’s authority.

Docker Compose remains the local deployment option. The native Kubernetes manifests deploy the application workloads without sidecars and use upstream Istio components. The dedicated mesh E2E suite verifies actual ingress, waypoint and ztunnel enforcement with API echo fixtures; the full application lifecycle E2E suite runs through the shared Compose proxy. See the Kubernetes deployment guide for dependencies, configuration, telemetry and the exact validation scope.

Configure model aliases server-side. No model weights are loaded into Gateway. Invariants

  1. Tenant and actor come from the authenticated request, never a model argument.
  2. Scribe has no PostgreSQL, SpiceDB, S3 or administrative credentials.
  3. A generation-scoped, expiring capability authorizes only tool invocation. Every invocation rechecks active identity, conversation permission and current resource permissions through Loth (SpiceDB and Cedar). A capability cannot grant a permission its actor lacks. Terminal generations invalidate it.
  4. PostgreSQL access uses Gateway’s non-superuser, NOBYPASSRLS role and transaction-local tenant settings. AGE traversal uses the existing bounded, tenant-scoped graph adapter; results are filtered per node, edge and evidence.
  5. Tools expose typed search, graph and causal operations, never arbitrary SQL/Cypher. Ontology labels are returned as data; unattributed graph properties are redacted. Client ontologies do not require hard-coded entity or relationship labels.
  6. Attachment URLs are created only after current resource permission and S3 ownership checks. Persist object references, never presigned URLs.
  7. Only administrator-configured model and MCP endpoints may be contacted. Delegation credentials go only to Gateway, never to external MCP servers. Internet and sandbox tools receive no database or application credentials.
  8. Prompts, reasoning, tool bodies and signed URLs are excluded from telemetry. Export metadata-only OpenTelemetry traces, metrics and structured logs through OTLP. Framework payload and exception spans are disabled.
  9. Historical answers can contain previously authorized evidence. Recheck evidence visibility before feeding such history to a new run; until complete provenance exists, history sharing is restricted to its original actor.
  10. Amarth may use every required tenant input, regardless of the requesting user’s raw-data visibility. Access to a root causal result follows that entity’s view permission. Publish bounded root statistics, without input identities, source features, raw observations or the complete causal chain. Historical causal results are rechecked against root access independently of raw evidence permissions.

Conversation transitions

idle -> pending -> completed | failed. Reservation and user message insertion are atomic. At most one generation owns a conversation. Message edits preserve immutable revisions and cannot race an active generation. Completion persists the assistant message before releasing the reservation.

Generation is owned by a server worker, independently of the WebSocket. Slow or disconnected subscribers cannot block persistence. Reconnection reads persisted generation events with a monotonically increasing cursor, then polls for more; it never restarts inference. Events and terminal messages share tenant-scoped foreign keys and forced RLS. Reasoning is not persisted.

Threads are independent conversations with independent authorization. Forking must copy only authorized messages and attachment references in one transaction; editing a message must not silently reinterpret earlier assistant answers.

Process-crash recovery is distinct from client disconnection: interrupted runs must become explicitly failed or be resumed by an external durable execution backend. Never automatically replay mutating tools. Gateway control-plane write tools need explicit action policies and idempotency before being enabled.

Verification

Write regressions before implementation: mixed tenant/actor attempts, forged and expired capabilities, revoked access, denied evidence, arbitrary query rejection, unknown models, oversized inputs, truncated upstream streams, slow/disconnected subscribers, replay cursors, message revisions, and S3 attachment isolation. Exercise the framework’s real tool loop with a deterministic test model and real PostgreSQL under the application role. Run all tests through Bazel.

The pipeline lifecycle E2E ends with the real private runtime and an independent OpenAI protocol fixture. Compare its tool-derived answers with PostgreSQL, check users with and without evidence access, root-only causal access, ABAC, revocation and cursor replay after client disconnection. Model quality and Mac performance require separate evaluation using the selected real model.

Full CPython and temporary approved libraries are an explicit deployment option. It adds one persistent controller (256 MiB memory limit). To enable the full CPython option:

  • Include infrastructure/docker/python-sandbox.yaml as an additional Compose file and select the python-sandbox profile.   • Scribe reaches the controller only through a private shared Unix socket (directory mode 0700, socket 0600), with compatible service UIDs. No API key or public network listener is required. Only these trusted services receive the IPC volume.

  • Each unprivileged worker has a read-only root, dropped capabilities, resource/time limits and a bounded temporary workspace. It creates a fresh uv virtual environment and installs requested libraries offline from hash-pinned wheels built into the image. The closed policy permits NumPy, Matplotlib, pandas, SciPy, SymPy, Pillow and scikit-learn, plus their reviewed locked dependencies. No arbitrary package names, versions, repositories, source builds or install flags enter the installer. Destroy the container after every result/failure; a scoped janitor reaps orphaned workers after controller crashes.

Document retrieval and ESKG

Document search is a separate, rebuildable projection of authorized evidence. ESKG continues to model entities, states, events and causal relationships. Document chunks and extracted relationships never enter entity_embeddings, entity resolution, Vision sinks or their ingestion topics.

Authority and lifecycle

Gateway owns source records, S3 access and authorization. A durable Pengolo upload atomically queues indexing; temporary uploads are excluded. Existing durable files are queued during migration. The same DocumentRetrieval application port serves GraphQL, chat tools and future plugin integrations.

Three tenant-protected tables hold units, features and indexing jobs. Units retain the immutable source checksum, parser location, revision and extracted relationships. Deleting or expiring the authoritative file removes access immediately. Database foreign keys cascade cleanup when the source is deleted. Published results must still match the current file checksum and published revision.

Workers claim jobs with SKIP LOCKED, renew the five-minute lease every 30 seconds, and reject stale publication. Indexing and renewal remain independently polled: a renewal waiting for a job-row lock must not suspend the transaction that owns that lock. Renewal failure cancels indexing; the job deadline cancels both futures. Indexing has a fifteen-minute job deadline, bounded input (25 MiB), text (1 MiB), pages (256), chunks (2048) and attempts (8). After parsing, all chunks are published for lexical search before model loading and enrichment. This checkpoint keeps the active lease and reports enrichment_pending; native inference failures cannot hide the extracted text. Transient model failures are retried with backoff. Exhausted jobs expose a failed status when no usable revision exists. Explicit reindex requests preserve an active lease for unchanged content and restart an exhausted job once its lease has expired.

The work revision survives automatic retries independently from the fencing lease. Each fully extracted and embedded passage is marked durably; subsequent attempts reuse those facts, vectors and the parsed checkpoint instead of rereading S3 or repeating OCR. Progress is monotonic within that work revision. Completing a passage resets the consecutive-failure budget, so a large document can span several bounded attempts. Explicit retries of exhausted jobs and replacement content start a new work revision. The additive migration preserves existing projections; passages created before completion markers existed are conservatively processed again.

Scribe receives bounded evidence over workload-authenticated private RPCs. It does not receive S3 URLs, storage credentials, database credentials or tenant authority. Project access is checked before embedding, recognition or candidate retrieval; source access is checked again before returning evidence. Graph expansion uses only the same authorized, live source scope.

Parsing and local inference

Text and CSV parsing preserve character spans. PDFium extracts PDF text with page numbers and serializes native calls. Structural chunking prefers paragraph, line and sentence boundaries with bounded overlap. A missing parser or model produces a visible warning.

Document embeddings use the pinned local Qwen3-Embedding-0.6B Q8 profile. Query instructions, weight checksum, pooling, quantization and dimensions identify the embedding space. Queries and chunks must share that profile. The Qwen adapter advertises text support accurately, rejects silent truncation and supports explicit contextual token-span pooling in its token mode. The document index currently uses structural chunks, not end-to-end late chunking or multimodal indexing.

Native PDFium extraction retains PDF page numbers and source spans. Pages without extractable text and PNG/JPEG/WebP images use the existing GLM-OCR adapter locally on CPU, with pinned artifacts in the document model cache. Images are bounded to 16 million input pixels and resized to at most 1600 pixels per side before OCR. The native worker retains admission on cancellation until it releases model memory. No OCR model is loaded for a PDF whose pages already contain text.

The selected direction for visual retrieval is Qwen3-VL-Embedding, with one versioned shared embedding profile for queries, text chunks and visual pages. This is not enabled by the OCR integration: the currently deployed Qwen3-Embedding adapter remains text-only. Equal vector dimensions do not make its vectors compatible with Qwen-VL or SigLIP. A future profile migration must reindex both modalities and preserve page/image provenance before enabling cross-modal search; OCR remains complementary for exact quotations and lexical retrieval.

Eru supplies the local knowledge projection:

  1. Extract grounded mentions and merge source-local duplicates. Repair an incorrect offset only when the copied mention occurs once in the source.
  2. Generate up to eight open-information triples in one relation pass, using either the remote backend or the local SLM. Additional explicitly mentioned entities may be supplied by that relation pass.
  3. Require both endpoints in an exact supporting quote. Reject invented or duplicate edges and, when Registry supplies an ontology, reject incompatible predicates or endpoint types. Empty results do not trigger another local relation pass.

Native JSON grammar constrains generation; Pydantic validates the complete schema including lengths afterwards. Expanding long bounded strings in repeated native rules caused a real llama.cpp failure, so grammar compilation omits string-length bounds while token budgets and output validation retain the limits. Contexts are reset and serialized between requests. Telemetry records counts, stages and error types without document contents.

Qwen3-0.6B Q8 is the default extraction model; Qwen3-4B Q4_K_M is selectable locally. Model artifacts use pinned revisions and local caching. Recognition first uses specific named mentions with word boundaries; otherwise it invokes the local model. Relation extraction prefers the configured service OpenAI model by default and can be switched to the local model through the environment settings below.

Search and ranking

The public query is documentSearch(input: DocumentSearchInput!). Inputs include project/file scope, MIME and date filters, mode, result count, cosine threshold and reranker relevance threshold. indexDocument(id: String!) queues an authorized source. The library UI displays excerpts, source locations, scores and warnings; Scribe exposes the same search as document_search, including to specialist agents.

Lexical mode uses French BM25 through pg_textsearch. Plain PostgreSQL development tests retain a text-search fallback. Semantic mode uses the exact embedding profile and an explicit cosine threshold. Hybrid mode fuses lexical and dense ranks before local reranking. Scores retain distinct meanings: cosine similarity, reranker relevance and graph score are not calibrated probabilities of correctness.

StreamingDiskANN supports 1024, 2048, 2560 and 4096 dimensions. Queries order directly by the distance operator. The installed extension failed at execution on expression indexes (attnum > 0), so nullable typed generated columns provide physical index attributes, with dimension-specific partial indexes. Only the matching column is populated. This currently stores one additional vector representation per feature; measure its storage cost when scaling. Unsupported dimensions use exact cosine. The database regression executes EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) and checks for the expected Index Scan for every supported dimension.

Associative mode runs the pinned official HippoRAG indexing and retrieval engine with Galadril’s grounded facts, local embeddings and recognition adapters. It uses passage/phrase nodes, synonym edges, upstream seed weighting and personalized PageRank over the authorized candidate view. Local reranking and graph ranks are fused by rank rather than by adding incomparable raw scores. Failures retain useful first-stage evidence with warnings.

Explicit source/checksum provenance connects document passages to actual ESKG entities and source observations. Both state and event permissions are checked before expansion and again before returning the ranking. Chat tools receive eskgRefs and can explore further through authorized graph/causal tools; generation provenance retains those permissions for later replay. Phrase strings remain retrieval hypotheses, separate from canonical ESKG identities. Temporal propagation and whole-corpus persistent HippoRAG indexing are outside this bounded integration. See the retrieval audit for the exact scope and benchmarks.

Configuration and validation

Compose enables a persistent local model cache. It may add entities copied from the evidence. This path skips local relation generation. Configure SCRIBE_OPENAI_API_KEY or that alias’s service key; interactive ChatGPT credentials are not used for background extraction. Eru’s OpenInformationPipeline supports open predicates for HippoRAG 2. A Registry OntologySlice can accompany private extraction requests; pipeline blocks can also use their existing task-bound Registry slice. The policy uses stable link_type resource IDs and their source_type/target_type attributes. The first local use downloads public weights; prewarm the cache for offline operation. Allow several GiB of RAM for simultaneous embedding, extraction and reranking. The default Kubernetes Scribe deployment leaves document models disabled; enabling its cache requires provisioning storage and increasing its memory budget.

The offline benchmark in tests/e2e uses attributed UCI Online Retail observations already ingested by the ESKG lifecycle test. Twenty-four passages and eight questions share customer IDs and source rows with that test. Real model outputs are cached, so ordinary regression runs do not recompute embeddings. Retrieval uses curated source-derived triples to isolate ranking quality. Eru’s actual cached extractions are evaluated separately for annotated-link recall and latency; this distinction avoids attributing perfect extraction to the ranker. See the fixture README for regeneration and measurement details.

The design is informed by HippoRAG 2, Contextual Retrieval, late chunking and MUVERA. Contextual prefix generation, adaptive semantic boundary models and multi-vector MUVERA indexing are not enabled by this implementation.

Indexing progress

The existing leased retrieval_jobs row holds a bounded stage and an estimated percentage. Reading, parsing/chunking, fact extraction, embedding and publication advance it from 0 to 95; successful publication removes the job and the ready source projects 100%. These percentages describe processing work, not confidence or remaining time. Early lexical publication remains available during enrichment. Retries and exhausted jobs have distinct states instead of reporting completion.

Gateway projects progress with each authorized library page in the same SQL statement. Updates validate the source checksum, expiry and current lease; a stale worker cannot update another attempt or a deleted file. Integer estimates bound progress writes independently of the number of chunks.

The visible library refreshes one page of at most 50 files every three seconds, rotating across pending files already loaded by the user. Refreshes bypass cached progress and retain pagination and previews. Hidden tabs, inactive library views, terminal jobs and completed indexing stop issuing progress requests.

Extraction credentials and retries

A provider HTTP 401 or 403 is published as graph_extraction_unauthorized alongside graph_extraction_unavailable. Parsed passages and existing embeddings remain searchable. The indexing job stops automatic retries and the library explains that extraction credentials need attention. After correcting SCRIBE_OPENAI_API_KEY (or the selected model’s service credential), recreate Scribe and use Index again; indexDocument reopens exhausted jobs.

Local entity proposals have a five-second wait budget and at most one outstanding native operation per runtime. A failed or slow proposal does not prevent remote relation extraction: the remote model may propose entities, and the same source grounding and Registry constraints still validate its result. The warning entity_extraction_skipped reports this fallback without scheduling redundant relation extraction.

Percentages retain their high-water mark across retries, while the stage tracks the operation currently running. A retry therefore cannot remain labelled as publishing merely because its previous attempt reached 95 percent.

Official engine and local adapters

The hipporag2 API mode now executes HippoRAG.index() and HippoRAG.retrieve() from the complete official package at d5c8329. third_party/hipporag/upstream/PROVENANCE.json fingerprints every Python source. The only upstream patch makes unused cloud/Transformers providers lazy imports; index construction, synonym KNN, linking, dense fallback and PRPACK PPR are unchanged. The former Galadril approximation has been removed from production code and tests.

The integration deliberately supplies Galadril components: grounded Eru facts, Qwen vectors and local recognition selections, with optional configured escalation remaining under the existing Scribe policy. It replaces upstream OpenIE and DSPy provider calls with typed evidence adapters. This is the official retrieval engine with local adapters, not a reproduction of the paper’s models or prompt evaluations. Scribe continues to own answer generation; upstream QA and its unauthenticated MCP server are not exposed.

If recognition retains no upstream linking candidate, the official engine uses its dense passage fallback. Responses report graph_dense_fallback and omit graph scores rather than inventing PPR evidence. The live lifecycle requires PPR runs in both official modes and separately validates this explicit fallback.

Upstream passage/fact/phrase stores are built from a Gateway-authorized view of at most 256 passages. One exact view is cached in a private temporary directory; source/fact/profile/link changes replace it and close its stores. No external index or pickle path is accepted. Chunk/fact embeddings produced during indexing are reused, alongside a bounded cache of local phrase vectors. Database/S3 authority stays in Gateway. This bounded candidate-view integration is not a persistent whole-corpus HippoRAG index and does not establish whole-Wikipedia scalability.

ESKG bridge and authorization

A pipeline can provide document_evidence in its raw payload, as one object or an array of up to sixteen {source_id, checksum} objects. IDs are immutable Pengolo file IDs; checksums are lowercase SHA-256 hex. Vision validates and stores this provenance on the source event. Gateway matches it to the current file revision, then follows actual entity_states observation identities. Matching names never create an identity assertion. No new document-to-entity table is introduced.

Before propagation, Gateway checks document ownership/project scope and separately checks both the ESKG entity-state and event permissions with their actual state type. Expansion follows shared authorized identities or source observations; discovered documents and their bindings are checked again. Revoked or changed graph evidence discards the graph ranking. Expired/deleted files and checksum changes cannot reuse an old view. Errors preserve usable first-stage evidence and return warnings.

The extension adds distinct ESKG entity and observation nodes to the upstream query graph, retaining upstream phrase nodes as retrieval hypotheses. It does not promote phrase similarity into canonical ESKG identity, infer causation, or implement a new temporal propagation algorithm. Relevant eskgRefs are returned to chat/plugin callers and recorded in generation provenance, preserving revocation checks during replay. Scribe can follow those references through the existing authorized graph and causal tools when the question needs broader state/event context.

GraphQL documentSearch exposes includeEskg (default true for associative mode), engine and eskgRefs. includeEskg:false provides the plain-engine ablation. Existing chat and library search routes use the same application port.

Chunking, fusion and reranking

The deployed chunker adapts to paragraph, line and sentence boundaries under fixed character budgets. It is structural chunking, not semantic adaptive chunking. Its exact source spans and overlap are regression-tested. The short passage corpus alone cannot establish the retrieval quality of a long-document chunking strategy.

Qwen’s default embedding profile uses its trained last-token pooling. Contextual token-span mean pooling is an experimental separate profile; document indexing does not currently use it. Qwen is causal: mean pooling its token outputs does not supply the bidirectional whole-document context assumed by the late-chunking paper. Do not mix these vectors with the default profile or claim paper-equivalent Late Chunking.

Hybrid search applies reciprocal rank fusion to BM25 and dense candidates. Local cross-encoders rerank the graph shortlist; associative mode combines their ranks with graph ranks using reciprocal rank fusion. Raw cross-encoder and PPR scores are never added together. Cosine, BM25, cross-encoder scores and PPR have different meanings; none is a calibrated confidence percentage. The cached benchmark compares BGE and Qwen on identical pairs and reports Recall@5, native CPU timing and peak process RSS. The live E2E additionally exercises actual pg_textsearch, DiskANN queries, GraphQL authorization and index lifecycle.

Runtime packaging

The engine is a private Scribe library, avoiding a second deployment and duplicate inference models. A separate CPU-only Torch lock and Bazel dependency hub avoid pulling Vision’s CUDA graph into Scribe. Shared wheels resolve to the main hub; large native libraries have explicit OCI layers. The local adapters do not import upstream’s incompatible optional Transformers/provider implementations. The tested runtime uses the workspace’s modern NumPy/Pandas/Pydantic and CPU Torch versions, not the upstream distribution’s old Torch/Transformers pins.

Private workload identity, request budgets, admission, content-free OTLP spans and read-only retrieval remain at the service boundary. A future independent service can reuse the same evidence-view contract; it must preserve authorization before all recognition, synonym expansion and graph traversal.

Kafka connects projections, not search requests

This is a proposed extension. The current document indexer still uses PostgreSQL jobs; existing ingestion pipelines already use Kafka. No new source outbox or independent HippoRAG Kafka consumer is claimed by this integration.

Reuse the existing Kafka/Redpanda deployment and pipeline event envelope. Gateway commits an immutable source revision and an outbox row in one transaction; an outbox publisher emits a versioned source event keyed by tenant_id:source_id. Consumers independently maintain document memory and ESKG projections. Do not couple either consumer’s transaction or availability to the other’s progress.

Events carry an event ID, correlation/causation IDs, source ID, monotonic revision, content checksum, object reference, MIME, selected pipeline revision, authorization revision and projection intent. They carry neither document bodies nor vectors, credentials or signed download URLs. Consumers resolve object references through workload identity and tenant-scoped access. Trace context propagates through headers; telemetry includes identifiers and durations rather than document content.

Delivery is at least once. Each projection atomically records its consumed revision with the resulting state; duplicates are idempotent, old revisions are ignored, and deletion tombstones prevent late retries from resurrecting sources. Kafka offsets advance only after durable application. Bounded retries, dead-letter metadata, operator replay and per-projection lag/status are observable. ACL changes and deletions invalidate searchable snapshots before asynchronous physical cleanup.

Synchronous search continues through authenticated APIs. Kafka is not a substitute for per-request authorization and does not grant permission to ingest into ESKG.

Future chatbot ingestion and pipeline authoring

Retrieval indexes source evidence without asserting ESKG truth. A future chatbot write operation is a separate command: analyze_source(source_id, revision, pipeline_id, pipeline_revision, target_projections). Gateway rechecks the current actor’s source read and pipeline execution permissions, resolves the immutable S3 reference itself, records an audit/outbox entry, then returns a durable execution ID. The UI can show independent ESKG and document-memory progress and partial failures.

Capability catalog contract

A capability is deployment metadata, not execution authority. Version 1 uses stable namespaced IDs, an origin (plugin or user), optional plugin identity, a kind (input, output, model, mcp, skill, algorithm), execution targets (pipeline, scribe), and an object JSON Schema for parameters. Optional step type and model class identify existing pipeline bindings. Descriptors never contain endpoints, credentials, or executable source. Catalogs are bounded, reject duplicate IDs and invalid namespaces, and fail closed on unknown contract versions. Built-in pipeline descriptors have one JSON source shared by Rust Gateway and Python. Execution status distinguishes registered bindings from declared metadata. It does not guarantee provisioned weights, reachable services, or permission to execute.

Gateway exposes authenticated pipelineCapabilities and scribeCapabilities queries with kind and plugin filters. Active tenant membership is checked before catalog access. Pipeline discovery reads the packaged runtime inventory through Scribe’s private /pipeline-capabilities route; Scribe tool discovery uses /capabilities. Both use bounded transport. A runtime failure is reported, never converted into an empty successful catalog. A disabled Scribe has an empty catalog. Model alias selection remains scribeModels.

Scribe accepts trusted injected tool extensions, each with an MCP or algorithm descriptor and a toolset factory. IDs are unique and tool names are prefixed by the full capability ID. Run requests explicitly select extension IDs; omitted selection exposes no injected extension. Unknown or duplicate IDs fail before admission and before invoking factories. Toolsets are created per run and use native PydanticAI lifecycle, timeout, tracing and tool-call budgets. MCP factories receive no Gateway bearer token. Native tools and legacy administrator-configured MCP URLs retain their current behavior. Public metadata never exposes MCP URLs.

The official plugin runtime now discovers packaged manifests, loads only reviewed factory paths, and binds pipeline capability_id selections. This boundary does not implement plugin downloads, tenant installation, tenant-selected imports, arbitrary new step kinds, or approval workflows. Trusted algorithm toolsets can use request dependencies, and must preserve Gateway authorization for private data and explicit approval for side effects. Catalog discovery grants no permission and no approval. Source selectors and microservice lifecycles are documented in the official runtime contract and plugins/README.md. Native branch routing is advertised by the core catalog and documented in Native pipeline branch routing.

User contributions and compatibility

Plugin and user contributions share the same contract. Plugin contributions carry plugin_id, plugin_version, and IDs in the plugin namespace. User contributions use the reserved user.* namespace, origin: user, and null plugin identity. The namespace identifies provenance; it does not identify a principal or authorize access. The server must derive ownership and tenant/project scope from trusted registration and authorization state, never from a submitted descriptor.

compatibility.allowed_models is an optional allowlist of exact runtime model identifiers: Scribe model aliases, or model class identifiers for pipeline composition. Empty means no declared model restriction. compatibility.requires is a bounded list of other capability IDs that must be explicitly selected in the same execution context. Dependencies are not automatically enabled, executed, or granted privileges. The validator checks every selected capability, so each dependency’s own constraints also apply. These are co-selection constraints, not an execution-order graph. Self-dependencies, duplicates, and oversized constraints are rejected.

CapabilityCatalog.validate_selection(ids, target=..., model=...) rejects unknown and duplicate IDs, missing dependencies, unsupported targets, unbound declarations, and incompatible models. GraphQL exposes origin, nullable pluginId/pluginVersion, execution, and typed compatibility fields through both existing discovery queries. Omit the plugin filter to include user items. Existing manifests default to plugin origin, registered bindings, and unrestricted compatibility.

Composition injection is not a tenant installation store. A runtime containing user contributions must be confined to their authorized tenant/project scope; do not install such contributions in a runtime shared across unrelated tenants. The current production composition registers no user contributions. Future user registration endpoints and tenant/project catalog resolution must enforce that scope before discovery or execution. Public pipeline configurations now select official capability IDs through the shared registry; user contributions still require separately scoped installation and authorization contracts. Portable SKILL.md loading and the approval resumption API remain separate work.

Agent teams

A team is a trusted, immutable composition of one to eight named agents. Every agent has a bounded mission and optional Skill IDs. team_id selects a registered team in the private Scribe run/generation request; a request cannot supply agent code, tool URLs, credentials, or extra permissions. The current model alias and selected tool IDs apply to the entire team. Unknown teams, missing Skills, and incompatible Skill/model selections fail before admission or factory invocation. Team registrations follow the same tenant/project scope rules as tool extensions.

Scribe uses PydanticAI’s programmatic multi-agent pattern. Workers execute in configured order with isolated message histories and the same authorized tools and generation-scoped dependencies. They receive the current request and prepared context, not the previous conversation or another worker’s report. The final orchestrator retains conversation history and receives bounded, attributed reports as untrusted data. Only its response is streamed to the user. Failure of a worker fails the team instead of silently synthesizing an incomplete result. One timeout, request budget, tool-call budget, and web-search budget cover the whole execution. Sequential execution avoids concurrent checks overspending the shared budget.

WorkflowSkill binds a Skill descriptor to bounded Python-defined workflow instructions. It uses PydanticAI’s native deferred Capability: metadata is visible first and the model calls load_capability to activate the instructions. Each worker receives only its assigned Skills; these workflows provide no tools, filesystem access, shell, or extra authority. Factories and MCP sessions remain per agent run. The existing portable SKILL.md/Harness loader remains separate; this workflow binding does not parse skill packages. Skill IDs and their model restrictions are exposed in the existing capability catalog. The private GET /teams endpoint lists team definitions without workflow instruction bodies.

This is request-driven execution. Recurring watches, scheduling, independent agent memory, public Gateway selection, and user registration UI are not part of this boundary. Selecting a team does not schedule future work.

Official plugin runtime contract

Official plugins are trusted, reviewed deployment code packaged from plugins/. Tenant pipeline definitions select capability IDs, never Python imports, service commands, credentials, or infrastructure endpoints. Discovery grants no authority to act on an external account. Third-party installation is outside this contract.

At startup an immutable registry discovers packaged manifests, checks ownership, versions, dependencies and execution bindings, and rejects inconsistent bundles. Pipeline bindings create one handler per published tenant/pipeline/revision/step. Models and algorithms use the same execution port as built-in steps. Scribe adapts toolset factories and packaged Skills to its existing approval and capability-selection contracts. Public discovery contains metadata only.

algorithm steps select capability_id. Inference may select a model capability instead of a built-in model name. Native route steps select routing: regex or routing: slm without capability_id and declare branches, mapping labels to immediate downstream step IDs. A handler returns branch alongside its payload. Only that branch advances. Unknown labels, empty branch maps, undeclared edges and destinations outside the immediate DAG are errors. The durable step result stores the decision; replays never ask a model to decide again.

Ingestion remains tenant-bound. Source group_id and content_types are optional conjunctive filters applied to the storage event, in addition to match_pattern. They are independent of source_kind and MIME-derived modality. A mail connector writes tenant/raw/email/...txt; an email source can select group email, parser text, and source kind email, while the payload remains text. Different published pipelines may consume the same source. Ambiguous sources within one publication remain errors. Project identity is not inferred from event metadata.

A plugin service is an independently deployed worker selected from its manifest, with a bounded cooperative shutdown lifecycle. Vision and Scribe never start arbitrary processes or receive a Docker socket. The deployment supplies account credentials, tenant, input group, storage permissions and OTLP settings. An IMAP worker must checkpoint only after confirmed ingestion, bound message size and poll batches, and use stable object identities for retries. Services are disabled unless explicitly deployed; discovering a plugin must not read or send emails.

Regex routing compiles expressions once and bounds evaluation time and input size. SLM routing uses Scribe model aliases, structured labels, bounded fallback and a shared deadline. See Native pipeline branch routing. Model output cannot add graph edges or authorize external actions. All extension calls participate in existing OTLP traces; telemetry contains IDs, outcomes and duration, never message bodies, tool arguments or account secrets.

The editor reads the authenticated live capability catalog and pins selected plugin versions in sources and steps. Gateway validates parameters and deployed versions on composition, creation, update and publication; unavailable versions fail closed. JSON Schema validation uses normalized source defaults consistently before and after Vision loads a published revision. Ordinary parameter schemas apply to plugin parameters, excluding engine-owned scheduling/retry fields.

Scribe model factories return native PydanticAI models with provider metadata. Their capability IDs become Scribe aliases, selectable in conversations, document extraction and native SLM routes. A removed alias follows the route’s configured fallback policy. Model capabilities are distinct from selectable tools and Skills.

The plugin package provides an authorized ingestion client and an explicit worker deployment renderer for Kubernetes and Compose. Ingestion obtains a scoped staging upload and finalizes through Gateway before returning a receipt. Shared HTTP credentials never accompany a presigned storage upload. Delivery has bounded payload/response sizes and a total deadline; it does not automatically retry mutations with an uncertain outcome. Image publication includes an amd64 and arm64 plugin worker, while services remain opt-in. The utils email service supplies authorized mail collection, Scribe drafts and controlled delivery. law business features remain deferred.

Native pipeline branch routing

Branch routing belongs to the current pipeline and works without plugins. The core catalog advertises core.route.regex and core.route.slm; pipeline definitions use a native strategy rather than a plugin capability ID:

name: document-routing
sources:
  - id: mail
    topic: raw
    match_pattern: '^tenant_a/raw/email/'
    group_id: email
    content_types: [text/plain]
    schema_path: schemas/avro/text.avsc
    parser: text
    source_kind: email
pipeline:
  - step: classify
    type: route
    routing: regex
    input_from: [mail]
    params:
      field: record.raw_payload.content
      pattern: 'dossier (?P<case_id>[0-9]+)'
      match_branch: legal
      default_branch: general
    branches:
      legal: [legal-processing]
      general: [general-processing]
  - step: legal-processing
    type: inference
    model: galadril_inference.models.embedding.qwen3.Qwen3EmbeddingModel
    input_from: [classify]
  - step: general-processing
    type: inference
    model: galadril_inference.models.embedding.qwen3.Qwen3EmbeddingModel
    input_from: [classify]

Replace the example model with a deployed built-in model or plugin capability. The regex block preserves the input and adds branch plus named extractions. Expressions compile once; matching runs off the event loop with a time budget. A missing field, oversized input or timeout fails the step and follows its retry policy. All labels must be declared, and branch destinations must cover exactly the immediate streaming consumers. Multiple destinations on one label fork the pipeline. Stateful joins remain unsupported.

For model-based decisions, use any alias configured in Scribe, including local OpenAI-compatible endpoints and API providers. The block uses the same model instances, provider settings and reasoning-effort validation as conversations:

- step: classify
  type: route
  routing: slm
  model: local-classifier
  input_from: [mail]
  params:
    field: record.raw_payload.content
    instructions: Choose legal for litigation correspondence, general otherwise.
    fallback_models: [api-backup, another-local-model]
    timeout_seconds: 60
  branches:
    legal: [legal-processing]
    general: [general-processing]

model is a Scribe alias, not a Python class or an environment-selected provider. Omit it to use Scribe’s default. Vision obtains the private Scribe origin from trusted connectors.scribe_endpoint (default http://127.0.0.1:8092 for the Compose egress proxy). A Kubernetes mesh bootstrap must use the Scribe Service origin, typically http://scribe:8091. Provider credentials remain in Scribe.

When fallback_models is omitted, Scribe tries the requested/default alias, then the current default and remaining configured models in catalog order. An explicit list restricts the alternatives; an empty list disables fallback. Missing aliases are skipped, including removals between attempts. At most three available models are attempted, with one agent model call per attempt and a shared total deadline (default 60 seconds, maximum 180). Timeout, connection failure, missing-model responses (404/410), throttling and server errors can advance to the next model. Authentication/authorization rejection stops the operation. A malformed decision or an undeclared branch fails closed; it never creates a destination.

The private POST /pipeline/route endpoint is restricted to Vision’s workload identity. It cannot access tools, conversation history, external actions or a user’s delegated account. Scribe’s concurrency budget also applies. Responses contain the chosen branch, actual model alias and whether fallback occurred. Vision persists this provenance with the step result; completed replays use the stored branch and do not call a model again. Regression tests use simulated local/API models and never send live provider requests.

Content and metadata

Dotted paths address the actual incoming payload: standard normalized metadata includes record.metadata.language, input_type, mime_type, and source_kind; source-specific fields remain under record.raw_payload. The title and date paths below are examples for records enriched with those fields by a source or upstream block. Routing does not invent or populate missing business metadata.

Both regex and Scribe routing read record.raw_payload.content by default, the text body produced by Intake’s text parser. Binary documents need a text extraction or OCR block before text routing. Set params.field to another dotted payload path to inspect a title or another textual field instead.

Scribe routing can receive an explicit whitelist of additional metadata:

params:
  field: record.raw_payload.content
  metadata_fields: [record.metadata.title, record.metadata.date]
  instructions: Choose legal for an appeal, general otherwise.

Only these fields accompany the text, as a bounded JSON object with content and metadata. Missing optional metadata becomes null. Credentials and other payload fields are not automatically sent to the model.

Transfers to another pipeline

A terminal native transfer selects a published tenant-local pipeline, an immutable Registry revision, and one receiving input. For example, a router’s legal branch can point to this block:

- step: legal-processing
  type: pipeline
  input_from: [classify]
  pipeline_ref:
    pipeline_id: law
    revision_id: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
    input_source: mail

The example revision must be replaced with the target’s actual published Registry revision. New drafts and publications must select the current published revision. Already published parent revisions retain their original pins when the child is updated. There is no implicit return: a transfer cannot have downstream blocks in the parent. Add any common processing before the transfer.

The Gateway filters selectable targets by View and Execute. Reading a linked revision requires View, and creation, update, and validation recheck both rights recursively before loading dependencies. Publishing also requires Publish on each linked pipeline, preventing authors from granting access to another graph through a parent publication without delegation authority. Tenant identity comes from the authenticated request, never from the reference. Permission failures use GraphQL FORBIDDEN; dependency failures do not expose raw storage errors.

The Registry compiler expands references into the root execution graph before Vision starts. Only the selected input’s event-driven descendants are attached; other inputs and independent scheduled blocks do not start. The payload passes through unchanged, so compatible input contracts are the author’s responsibility. A transfer neither rereads IMAP nor creates another ingestion job. The original execution identity and durable branch results remain in use. Compiler-owned provenance resolves each child block’s ontology against the child’s pinned revision; payloads and authored definitions cannot forge that provenance.

Admission limits apply to the full composition:

  • At most three cross-pipeline transfer occurrences, including nested and repeated references. Ordinary local router branches do not consume this budget.
  • At most 256 source and processing blocks after inclusion. Each occurrence of a referenced definition is charged, including its source contracts and independent input blocks, so selecting an input cannot hide an oversized graph.
  • Cycles are rejected by pipeline identity even when a cycle uses different revision IDs. Stateful joins and continuations after transfers are rejected.

The dashboard offers native regex, Scribe, and metadata routing, labeled branch connections, and a permission-filtered pipeline picker with receiving input selection. Linked contents expand read-only and are reread under current access rights on each expansion. Server validation supplies the authoritative expanded block count before YAML export. The exported definition preserves references; internal forwarding blocks and provenance are never authored by the browser.

Ontology and pipeline Registry

Registry is the single persistence and semantic authority for tenant ontologies, pipelines, publications, and pipeline-to-ontology bindings. Gateway and Vision use the versioned galadril.registry.v1.Registry gRPC contract. Neither service receives lakeFS credentials, repository names, object paths, or storage namespaces.

Registry maps each validated tenant identity to an opaque, server-owned lakeFS repository and path. lakeFS stores immutable revisions while S3 remains the physical object store. A lakeFS commit ID is returned unchanged as an opaque Registry revision ID and is used for optimistic writes, publication pinning, and reproducible Vision execution.

Tenant lifecycle is also owned by Registry. Internal callers may validate only a bounded, explicitly supplied list against Registry-owned S3 markers. Empty validation requests are rejected and Registry exposes no tenant enumeration operation. Reads fail closed for missing tenants; artifact insertions initialize the server-derived S3 marker and lakeFS repository when necessary. The tenant deletion RPC requires an exact repeated tenant ID and exists solely for irreversible GDPR erasure of both lakeFS metadata and physical S3 objects.

The current service deliberately contains no mTLS or application authentication implementation. A deployment proxy will authenticate service identities and authorize these internal RPCs; Registry still validates every payload and storage-derived identity instead of treating the future proxy as input validation.

Semantic ownership

For every immutable revision, Registry reconstructs the ontology graph and pipeline DAG from the stored artifact state. Its canonical Rust implementation:

  • validates resource identities, kinds, owners, links, and value types;
  • resolves inheritance, interfaces, references, and dependency closures;
  • detects cycles, dangling references, and incompatible inherited properties;
  • validates pipeline nodes, edges, step types, and ontology bindings;
  • performs resource-aware semantic diffs and three-way merges.

Inheritance and interface edges form a directed acyclic graph. For example, object.pilot may extend object.person: the effective Pilot type inherits property.person.name and adds its own property.pilot.flight_history. Dependency-closed slices include the selected type, its ancestors, and properties owned by each type, so Vision receives the complete effective contract without implementing inheritance itself.

Semantic merges never invoke lakeFS file-level merge. A successful merge is validated and committed as a new Registry revision; a conflicting merge returns structured conflicts without changing storage. Derived graphs may be cached by revision ID, but the cache is disposable because every graph is reconstructible from its immutable revision.

Ownership boundaries

Gateway authenticates users, applies SpiceDB and Cedar authorization, preserves PostgreSQL RLS, and records audit/access events. Audit rows may refer to opaque Registry revisions, but PostgreSQL does not persist ontology or pipeline artifacts.

Vision workers load an explicitly selected tenant pipeline and block-local ontology slices by tenant, pipeline, block, and immutable pipeline revision. They retain the FastStream, Kafka, and Ray execution architecture and never accesses lakeFS.

Registry intentionally exposes no history-listing API. lakeFS commits are an internal versioning primitive, not application history. Searchable and auditable artifact history will be designed separately in PostgreSQL.

Initialization boundary

This architecture has not been deployed, so there is no legacy data importer and Registry contains no legacy database read path. Prototype state is discarded; ontologies, pipelines, publications, and bindings are authored afresh through Registry and committed directly to lakeFS. The unshipped PostgreSQL pipeline prototype migration is removed; Gateway migrations contain only audit/access and unrelated application tables.

Intake service

Intake service is a Rust binary located in services/intake/. Its sole responsibility is ingestion.

Initialization Phase

At startup, Intake reads trusted settings from connectors.yaml, loads local Avro schemas, and connects to Kafka, S3, and the Registry gRPC API. Pipeline routing definitions come only from published, non-deleted tenant revisions returned by Registry. Compiled routes expire after five seconds. See pipeline storage.

The Event Loop

The service continuously listens to the S3 bucket notification topic. When a file arrives:

  1. Authorization: It extracts the exact tenant partition from the object key and asks Registry to verify the tenant’s S3 marker for that request.
  2. Routing: It compares the tenant-scoped path with every published source rule. A shared source can produce one route for each matching immutable pipeline publication.
  3. Parsing: It downloads the tenant object once and selects the configured parser for each route.
  4. Emitting: It publishes the parsed record with mandatory galadril-tenant-id, galadril-pipeline-id, and galadril-pipeline-revision Kafka headers. Vision rejects missing, malformed, or conflicting identity metadata.

S3 keys are partitioned as <tenant>/raw/... and tenant comparison is exact and case-sensitive. Intake does not create PostgreSQL temporary state. Components that use PostgreSQL set the tenant transaction context before accessing tables protected by row-level security.

Vision Service

Vision Service is the brain of the platform, located in platform/vision/. It is dynamically orchestrated by the galadril-pipeline library. It relies on the galadril-inference library to standardize calls to ML algorithms.

Execution boundary

The application layer owns command admission, published step selection, and ontology binding. It depends on pipeline and ontology contracts and a structural StepHandler port, never on Ray, Kafka, S3, PostgreSQL, or inference engines. Handlers receive an already admitted command and its published step definition; they return a JSON object. They cannot select the route used for admission.

The actor composition root builds one route per execution identity and injects handlers by published step ID. An execution identity pins a tenant, pipeline, and revision. A command must match that identity, tenant, step ID, and step type before any handler or ontology lookup runs. Duplicate routes, duplicate steps, and missing or unknown handler bindings fail during construction. Route tables and step definitions are snapshotted at construction.

The built-in adapter retains the current inference, resolution, transactional sink, and causal implementations. Each route owns its adapter, S3 client, and PostgreSQL state; configuration from one route must never initialize another route’s connections. Routes with identity resolution enabled for the same tenant share one resolver owner and must agree on its configuration and database. Incompatible identity bindings fail during composition. Pools and models are reused across commands within their ownership boundary. The actor preserves context and accelerator cleanup after success and failure. Existing Ray spans and structured OTLP logs continue to wrap execution, including injected handlers.

Trusted Python composition can replace individual handlers, including resolution and persistence, without changing command admission or the actor transport. Handler bindings come exclusively from trusted Python composition. Pipeline documents and command payloads cannot supply new handler factories or backend credentials through this boundary. Existing configured model imports remain unchanged. This boundary now also hosts the trusted handlers registered by the official plugin runtime; it is not a sandbox. Handlers remain trusted service code and own their backend transaction, tenant isolation, idempotency, and resource lifetime contracts. The built-in sink keeps its PostgreSQL/AGE/vector/authz transaction together; splitting it into independent graph and vector ports would lose that guarantee.

This first boundary does not make all Vision infrastructure interchangeable: streaming startup, the execution ledger, and causal/query internals still use PostgreSQL. Local examples retain their unscoped execution behavior. Production routes come from validated Registry publications. There is currently no trusted project identity in the runtime contract; project selection requires a future Registry-owned binding, never a project ID supplied in command attributes. Official plugin discovery binds packaged models, algorithms and outputs through capability IDs. Native branch routing uses regex or Scribe models independently of plugins. Generic algorithm and native route steps retain the same command admission and ontology boundary. Packaged MCP toolsets and workflow Skills use Scribe’s existing selection contracts. Third-party installation and project identity remain outside this runtime contract.

Trusted composition uses VisionCommandProcessor(configs, handler_factory=build_handlers). The factory receives one snapshotted VisionConfig per route and returns a mapping from every published step ID to a StepHandler. Multiple steps may share one route-owned adapter. An alternative sink implements async execute(command, step) -> dict[str, JsonValue] without PostgreSQL types. Custom factories are responsible for preserving a single identity sequence owner when sharing a tenant across routes. Production deployment still uses the built-in composition; exposing reviewed official implementations in Registry is a later stage.

DAG Construction

Service loads runtime settings from connectors.yaml and asks Registry for one explicitly configured tenant and published pipeline. Registry validates the tenant marker and returns the DAG pinned to an opaque immutable revision. Each process keeps that tenant-specific route and ontology context while sharing its Kafka consumers and Ray CPU, GPU, and causal actors. An explicitly selected pipeline.example.yaml remains available for local examples. See pipeline storage for deployment and revision activation. If the tenant or publication does not exist yet, Vision waits with bounded exponential backoff (1–30 seconds) and emits pipeline.publication.pending over OTLP. Registry unavailability and deadlines also retry. No Kafka consumers or Ray actors start until the requested publication is validated. Invalid scope, invalid artifacts and authorization failures remain fatal. Provision the configured tenant and publish its pipeline through Gateway; startup never creates a tenant or substitutes a different DAG. Registry validates cycles and dependencies before publication. Vision computes only the execution order needed by its local runtime.

Dynamic Model Loading

Models are not hardcoded. Service uses Python’s importlib to instantiate the exact classes defined in the configuration. Model weights are automatically pulled from S3 into memory before processing begins.

Message Routing Loop

  1. The service polls batches of messages from Kafka.
  2. It validates the immutable tenant, pipeline, and revision Kafka headers and ensures the payload tenant agrees with the trusted header.
  3. It selects exactly one published DAG by (tenant, pipeline, revision) and resolves the configured source within that DAG.
  4. It passes the data to the model through a shared Ray resource pool.
  5. After every command, including failures, the Ray actor clears request context variables, runs Python garbage collection, and clears the CUDA cache for GPU commands. LI-ESKG retains only its internally tenant-isolated runtime.
  6. Once the model outputs a prediction, the service asks the selected DAG which step consumes the output next.
  7. If no step needs it, the data has reached the end of the pipeline (a Sink).

Data Sinks

When data reaches the end of Python pipeline DAG, it is saved into PostgreSQL. Galadril uses two extensions to handle AI outputs.

1. Apache AGE (Graph Storage)

We use Apache AGE to store:

  • Vertices: People, Bank Accounts, Documents.
  • Edges: Relationships like APPEARS_WITH (Person A in Image B) or TRANSACTED_WITH (Account A sent money to Account B).

2. pgvectorscale (Embedding Storage)

AI models output embeddings representing faces or text. We use pgvectorscale to store these arrays and perform blazing-fast similarity searches (e.g., finding the closest known face to an unknown detected face using ORDER BY embedding <=> query_vector).

Eru – ESKG Extraction

The document retrieval projection also reuses EruEngine through eru.documents.DocumentPipeline. Its local path extracts source-grounded mentions, merges duplicates, proposes bounded nearby pairs and generates all relationships in one batch. A direct local fallback handles missing entity pairs. Every accepted relationship retains an exact supporting quote during validation; these retrieval hypotheses do not establish ESKG identities or states.

The llama.cpp backend enforces JSON grammar, resets its context between requests and validates the full Pydantic result. Runtime failures log only stage metadata and error types. The cached retail benchmark records actual extraction outputs separately from the curated graph used to isolate retrieval quality.

eru is a production-ready, agnostic pipeline designed to extract highly structured Knowledge Graphs (Nodes and Edges) from unstructured text.

Why does it exist?

Extracting knowledge graphs using LLMs alone is flawed: they hallucinate entities, fail to strictly follow JSON schemas, and consume massive amounts of tokens (which is slow and expensive). Conversely, traditional NER (Named Entity Recognition) models extract entities perfectly but cannot understand complex relationships or implicit intents.

Eru bridges this gap. It forces small, fast LLMs to act only as logical routers between physically extracted entities, guaranteeing deterministic, hallucination-free graph extraction.

The 3-Layer Architecture

Eru processes text through a strict, three-step pipeline:

LayerDescription
ExtractionUses a Bi-encoder (GLiNER) to find physical entities in the text (e.g., Persons, Locations). It automatically deduplicates identical entities.
ReasoningUses a SLM constrained by outlines. The LLM is forbidden from inventing physical entities; it can only draw relationships using the IDs from Layer 1, or generate implicit conceptual nodes.
ValidationA logical gate that prunes mathematically impossible relationships (e.g., a “Car” cannot “Authorize” a “Person”) before the graph is saved to your database.

Here is a minimal example of how to use Eru to extract a graph from a simple sentence, allowing the model to deduce the implicit intent behind the action.

import json
from typing import Literal
from pydantic import BaseModel, Field
from transformers import AutoModelForCausalLM, AutoTokenizer
import outlines

from eru.engine import EskgEngine
from eru.extractor.gliner import GlinerExtractor
from eru.reasoner.outlines import OutlinesReasoner
from eru.logic.eskg import EskgLogicValidator
from eru.types import RelationDef


# 1. Define your Graph Schema
class Node(BaseModel):
    id: str
    text: str
    type: str


class Edge(BaseModel):
    source_id: str
    target_id: str
    relation_type: Literal["buys", "has_intent"]


class DailyGraph(BaseModel):
    entities: list[Node]
    relations: list[Edge]


def main():
    text = "Alice purchased a Macbook today because she wants to learn coding."

    # Layer 1: Extract explicit physical entities
    extractor = GlinerExtractor(
        labels=["PERSON", "PRODUCT", "TIME"],
        threshold=0.3,
    )

    # Define relationship rules for the LLM
    rules = [
        RelationDef(
            name="buys",
            description="When a person purchases an item.",
            allowed_sources=["PERSON"],
            allowed_targets=["PRODUCT"],
        ),
        RelationDef(
            name="has_intent",
            description="The implicit reason or goal behind the action.",
        ),
    ]

    # Layer 2: Setup the SLM Reasoner
    model_name = "Qwen/Qwen2.5-0.5B-Instruct"
    hf_model = AutoModelForCausalLM.from_pretrained(
        model_name, device_map="auto"
    )
    hf_tokenizer = AutoTokenizer.from_pretrained(model_name)
    llm = outlines.from_transformers(hf_model, hf_tokenizer)

    reasoner = OutlinesReasoner(
        model=llm,
        relation_defs=rules,
        open_entity_types=[
            "INTENT"
        ],  # Allow LLM to invent concepts like 'learning to code'
    )

    # Layer 3: Setup the Logic Validator
    validator = EskgLogicValidator(
        get_entities=lambda g: g.entities, get_relations=lambda g: g.relations
    )

    # Run the Engine
    engine = EskgEngine(
        schema=DailyGraph,
        extractor=extractor,
        reasoner=reasoner,
        validator=validator,
    )
    graph = engine.process(text)

    print(json.dumps(graph.model_dump(), indent=2))


if __name__ == "__main__":
    main()
