Galadril Documentation

Spatial maps and event localization

Status: proposed architecture, 2026-10-16. This document precedes backend implementation. The schemas, APIs, worker, limits, and performance objectives below are proposals, not existing capabilities. No frontend implementation is included. Decisions marked as a release gate need evidence before that release.

Purpose and feasibility

Galadril should accept user-supplied floor plans and 3D environments, optionally anchor them to Earth, and display authorized observations at precise locations. The same model must support a standalone building and navigation from a world view down to a room. This is feasible with the current PostgreSQL/PostGIS, S3-compatible storage, Kafka, Vision, and Gateway architecture. It requires a spatial domain and asynchronous asset preparation, rather than a file field added to an event.

Three independent concerns must remain explicit:

  1. Physical space and evidence: where an observation occurred, in which reference frame, with what uncertainty, and according to which calibration.
  2. Representation: an immutable plan/model revision, its layers, and the transformation from asset coordinates into that space.
  3. Presentation: which tiles, levels of detail, and authorized events a client needs for its current viewport and time window.

A new drawing must not move historical observations. Deleting a map must not delete badge or camera evidence. Zooming must not require downloading an entire country, building model, or event history.

Domain and immutable references

Identifiers are opaque and tenant-scoped. Every foreign key includes the tenant; physical storage keys and client names do not confer identity.

ResourceMeaning and versioning
SpatialSpaceStable identity of a site, building, floor, room, or standalone local environment; optional authorized ESKG Entity reference
SpatialFrameRevisionImmutable origin, units, axes, dimensions, parent frame and transform; explicit validity interval and recorded time
SpatialMapUser-visible map identity, owner, permissions, lifecycle, current published revision
SpatialMapRevisionImmutable source asset, source digest, space, frame revision, asset-to-frame transform, layers, bounds, processing recipe and manifest
SpatialLayerRaster/vector/model overlay with its own immutable revision and security boundary; a floor is a semantic space, not merely a layer name
SpatialAnchorRevisionStable landmark identity plus immutable position/region in a frame; can describe a door, reader, camera or zone
SensorPlacementRevisionSource/device identity, anchor or pose, applicable interval and calibration revision
SpatialLocalizationImmutable interpretation of an event’s position/region, provenance, frame and calibration; may supersede an earlier interpretation

Space containment is an acyclic semantic hierarchy. Frame parenting is a separate, bounded transformation tree; a semantic parent does not imply a usable transform. A frame revision references a specific parent revision, never a floating current. Re-anchoring creates a new revision and does not overwrite the old tree. A local space can remain usable without any Earth ancestor.

Buildings, doors, sensors and rooms can be ESKG Entity instances classified by immutable Registry ontology references. Badge accesses and detections remain Event. No Building, Map, or Room AGE label is introduced. OCCUR can relate an event to a known place Entity under the existing contract; frame and asset metadata remain relational. A spatial association must not fabricate an identity decision or an authoritative OCCUR edge from uncertain evidence.

Registry continues to own ontology/pipeline definitions. Map bytes and map revisions do not belong in the ontology store or its lakeFS physical layout. Pipeline configuration may pin validated frame/calibration references through a new typed spatial binding, checked for tenant, compatibility and permissions before execution. A payload cannot select arbitrary Registry revisions.

Coordinates and georeferencing

Canonical frames

Use named coordinate fields at application boundaries. Reject NaN, infinity, partial coordinates, impossible bounds, singular transforms, and mismatched dimensions. Unknown position or height remains unknown, never (0, 0, 0).

FrameCanonical representationRules
Earth geographicNamed longitude/latitude in degrees, optional ellipsoidal height in metresWGS84; persisted horizontal projection SRID 4326
Earth CartesianECEF x/y/z in metresEPSG:4978; used for globe placement and composing local transforms
Local metricRight-handed x/y/z, metres, Z up; x/y allowed for a 2D floorExplicit frame revision; axes have no compass meaning until calibrated
Asset/image inputDeclared pixel or model coordinatesSource evidence only; explicit transform into a canonical frame

External GeoJSON uses longitude then latitude, with optional ellipsoidal height, as specified by RFC 7946. Local metre or pixel coordinates are not published as RFC 7946 GeoJSON. Adapters must explicitly convert the existing internal [latitude, longitude] lists; changing an array’s interpretation silently would corrupt positions. EPSG axis conventions are not inferred from a two-element list.

Persist local geometry with SRID 0 and a required frame revision ID. SRID 0 alone is not a coordinate system. Every local spatial predicate first filters the exact frame revision and tenant, or transforms through an explicitly validated path. Never insert arbitrary tenant frames into global spatial_ref_sys, or relabel local metres as SRID 4326.

Use PostGIS geometry for indexing and appropriate metric projections or geography for geographic distances. Most ordinary predicates/indexes are 2D: floor identity and vertical bounds need explicit checks. Adding Z does not turn a 2D intersection into room-volume collision detection. An n-dimensional index is a later optimization with query-plan evidence.

Placing a building on Earth

A GPS point provides an origin; it does not establish orientation, scale, height datum, or a complete building footprint. Accept it as incomplete georeferencing and keep the plan usable locally. Require scale/units, orientation and a validated origin or control-point solution to publish an Earth placement. Separate height above an ellipsoid from height above sea level or a building’s floor datum; a missing datum cannot yield an exact global height.

For a calibrated local frame, compose:

asset position -> local metric frame -> local ENU frame -> ECEF -> WGS84

The ENU-to-ECEF step is a rigid transform around a declared origin; the geographic conversion is nonlinear. A single affine matrix from local metres to latitude/longitude is invalid at Earth scale. PROJ’s topocentric conversion defines the ENU/ECEF boundary. Pin the conversion recipe, datum/grid data and library versions; reject unavailable required grids rather than silently using a different datum. ST_Transform changes coordinates; ST_SetSRID only changes their label.

Initial calibration supports a declared metric plan and a rigid placement. Later scanned plans can use a fitted 2D affine transform with at least three non-collinear control pairs, or a planar projective transform with at least four suitable control pairs. Store residuals, control-point provenance and validity domain; reject degenerate fits. One or two GPS points must not be advertised as a full projective calibration.

Matrix serialization is fixed: 16 float64 values, column-major storage, homogeneous column vectors, p_target = T_target_from_source * p_source. Image inputs declare origin and axis direction, normally top-left/X-right/ Y-down. glTF uses a right-handed Y-up system and metres; its adapter to the local Z-up convention can map (x, y, z) to (x, -z, y) before placement. Keep format conversion separate from georeferencing. These conventions follow the glTF specification.

Historical queries default to the localization/frame revisions recorded with the event. Rendering that evidence on a later plan requires an available transform chain and returns its provenance. If no valid path exists, return UNPROJECTABLE; do not guess or rewrite evidence.

PDF/SVG are not initial direct-render inputs. They need isolated rasterization or sanitization first; arbitrary active documents never reach the browser as trusted map content. A texture image cannot produce a 3D building, and a mesh alone does not identify its doors/rooms. Such semantics require supplied or manually configured anchors. A generic GLB-to-city-scale tiler is not assumed to exist: qualify the actual converter, quality, licence and operating cost before accepting that input at that scale.

For 2D Earth layers, use explicit tile-matrix metadata, bounds, resolutions, minimum/maximum zoom and source attribution, following OGC Tile Matrix Sets. Web Mercator is a presentation profile with polar limits, not the canonical coordinate system for all of Earth. Handle antimeridian-crossing views as split regions and retain polar data for a suitable projection/globe. Local raster pyramids use their own declared bounds and resolutions; they are not Web Mercator XYZ by accident.

For large 3D data, OGC 3D Tiles provides hierarchical streaming. Bounding volumes and geometric error guide client detail selection; do not invent a proprietary mesh-zoom scheme. Globe, city, building and room content can occupy different hierarchy levels. Event overlays remain independent from static asset tiles so each new badge event does not regenerate the building.

PostGIS already supports vector tile generation through ST_AsMVT. Use bounded, indexed queries and prepared static tiles rather than unrestricted on-demand simplification. For raster preparation, GDAL’s COG driver supports an optimized source representation; an ordinary browser image loader still needs an appropriate reader or image tiles.

Client materialization contract

GraphQL returns metadata and a manifest reference, not base64 assets, complete meshes or arbitrary JavaScript configuration. A versioned manifest contains:

  • Map/revision/layer identities, space/frame revisions, validity interval and contract version.
  • Asset type, media type, immutable digest/size, bounds, dimensionality and explicitly directed transforms.
  • Tile matrix or 3D Tiles entry point, detail limits and supported compression extensions; a client must reject unsupported required capabilities.
  • Stable semantic feature IDs, floor/anchor references and attribution.
  • Authenticated relative delivery routes and overlay API capabilities.

Do not put expiring URLs, user credentials, event data, scripts, unrestricted styles or private layers in a broadly cached manifest. Sensitive layers have separate manifests and authorization boundaries. Child tile/texture URIs must stay inside the authorized revision; authorizing tileset.json alone is insufficient.

Three.js can load building assets with GLTFLoader. For the geographic client, evaluate MapLibre with Three.js layers, or CesiumJS for a globe with terrain and hierarchical 3D content. Official MapLibre examples and CesiumJS documentation demonstrate these capabilities. The recommendation is to keep both possible; a renderer choice is not required to implement the backend contract.

Use float64 for authoritative transforms and positions. Clients convert to camera-relative/local float32 buffers to avoid global-coordinate GPU jitter, reuse marker instances, and dispose of evicted tile resources. A headless consumer must reconstruct a known anchor from the manifest before the backend contract is declared renderable; a UI is unnecessary for that test.

Earth imagery, terrain and base-map datasets are separate licensed sources. World coordinates and zoom support do not supply a Google Maps-equivalent dataset. Start with configured, approved providers or self-hosted datasets, retain attribution and coverage, and do not bake a provider or API key into tenant map files. Routing, navigation and reconstruction from photographs are outside this feature’s initial scope. Indoor navigation can later use an IndoorGML-compatible topology without changing event localization.

Storage, processing and deletion

PostgreSQL and S3 ownership

PostgreSQL holds metadata, small validated transforms, bounds, anchors, operational geometries, job state, idempotency records, audit and replay data. S3 holds original files, textures, meshes, static tile pyramids and derived manifests. Feature rows needed for queries are bounded materializations, not a duplicate unbounded JSON copy of an uploaded dataset.

Proposed dedicated private spatial bucket keys:

<tenant>/spatial/maps/<map>/revisions/<revision>/source/<asset>
<tenant>/spatial/maps/<map>/revisions/<revision>/derived/<recipe>/<asset>

Staging keys bind tenant, actor, upload session and server-issued nonce. Source and derived keys are generated server-side and never overwritten after publication. Digests are integrity checks, not permissions. Deduplication, if added, is tenant-local to avoid cross-tenant existence disclosure.

Gateway owns spatial_spaces, spatial_frame_revisions, spatial_maps, spatial_map_revisions, spatial_layers, spatial_anchors, spatial_sensor_placements, upload sessions, jobs and lifecycle outboxes. Vision owns event_localizations, their correction history and a spatial event-publication outbox. A proposed spatial feed projection has one writer, the Vision publication/reconciliation path. Gateway reads it, never produces duplicate evidence from mutations.

Use Gateway SQLx migrations for control-plane tables and Vision’s migration path for event tables. Add forced RLS, USING and WITH CHECK, tenant-qualified foreign keys, enum/check constraints, and startup security verification. Worker roles get narrow job/result access rather than broad access to tenant event tables. Maintenance uses a separate identity and audited entry point.

Existing eskg_events identity includes event time in its composite primary key. Localizations must reference the canonical (tenant, event_id, event_time) without assuming event_id is SQL-unique. Introduce a Vision-owned canonical identity guard if enforcing one time per ESKG event ID across time partitions; audit conflicting legacy IDs before migration rather than picking one.

Indexes start with tenant/frame/space/time B-trees and local/global GiST geometry indexes. Global geographic projections are nullable derivatives of local evidence; unanchored events remain queryable locally. Time-partition high-volume localization/feed data with explicit retention. Verify PostGIS, PROJ, raster functionality and chosen drivers on the actual AMD64/ARM64 image; the presence of the core extension does not prove every converter is available.

Upload and publication state machine

Map revisions progress through UPLOADING -> VALIDATING -> PROCESSING -> READY. Failures enter FAILED; retries create a new fenced attempt against the same immutable source. Cancellation/deletion prevents later publication. A mutable map’s published pointer changes only through a compare-and-set on the expected previous revision. A new import never makes a working old revision disappear.

  1. Authorize creation/editing and atomically reserve tenant/actor byte, map and concurrent-job quota. Record durable audit and idempotency scope, then issue a short-lived staging upload capability.
  2. Finalize only the exact session/key owned by that principal. Re-check live access and declared/observed size, media signature and checksum. Do not trust filename, content type, ETag as a universal content hash, object tags, caller-provided bucket, or caller-provided tenant.
  3. Pin an immutable source before conversion. Presigned PUT URLs can be reused before expiry, so a staging HEAD followed by an unconditional copy is insufficient. Copy a verified object version, or use a tested conditional promotion plus digest verification of the destination; reject if the backend cannot guarantee this. The worker reads only the promoted key.
  4. Commit source metadata, preparation intent and audit together. Recover objects copied before a failed SQL commit through a reconciler. Do not claim an S3/PostgreSQL transaction exists.
  5. The worker leases a job with deadline and monotonically increasing fencing token; validate source, sanitize, convert and write immutable outputs. Bound retries; retain structured failure codes and quarantine diagnostics.
  6. Gateway validates the fenced completion and re-checks initiator access for delegated work. Mark processing ready only after all output digests and required spatial grants are acknowledged. Publish the pointer, audit and notification intent atomically; serving still requires current access.

Follow the same choreography for concurrent finalize, retries and cancellation. Idempotency keys include tenant, actor, operation, target and request digest; reusing one with different inputs returns a conflict. A worker that loses its lease cannot publish stale outputs. Sweep expired staging objects, incomplete multipart uploads and unreferenced derived outputs after a grace period.

Sandbox converters with no outbound network, read-only base filesystem, bounded scratch disk/CPU/RAM/runtime and a minimal driver allowlist. Reject path traversal, symlinks, external texture/document URLs, nested archive bombs, oversized decoded images, excessive vertices/tiles and unsupported required extensions. Internal relative asset references must resolve within the revision package.

Use shared connectors.s3 configuration with a spatial bucket setting and service-specific restricted credentials; do not duplicate Registry’s lakeFS credentials. The separate spatial bucket avoids lake PUT notifications feeding Intake. Any deployment choosing a shared bucket must prove equivalent routing isolation. Preparation jobs originate from committed Gateway state, not from untrusted storage notifications.

Deletion and recovery

Deletion returns an operation receipt. First atomically mark the map DELETING, stop new delivery/publication, invalidate sessions, and persist audit and cleanup intent. Gateway delivery checks this state even if a SpiceDB grant remains during reconciliation. Revoke spatial relationships, then asynchronously delete source/derived objects, versions, staged uploads and multipart parts. Complete DELETED only after verified cleanup, retaining a minimal tombstone and audit under configured retention.

Already downloaded bytes cannot be revoked. The default authenticated route re-checks every request; it cannot retract an in-flight response. Optional presigned GET/CDN capabilities have an explicit maximum revocation delay and must not be enabled when immediate future-request denial is required. S3 presigned URLs are capabilities until expiration or credential/policy invalidation, not a live SpiceDB check.

Event evidence, localization, minimal referenced frames and calibration provenance survive map deletion under their own retention policy. Deleting a referenced space/frame is a distinct operation and is rejected while evidence requires it. Source assets needed for retained evidence follow a declared evidence-retention policy rather than silently disappearing. Backups must restore metadata and required S3 objects consistently; reconciliation verifies manifests and records missing assets as unavailable, never silently recreates them.

Events at precise locations

Extend ObservationContext through an additive, nullable, versioned location record; retain legacy WGS84 fields through an explicit adapter. Avro defaults, Schema Registry compatibility, Intake parsing, Vision’s Pydantic model, normalization, localizer, sink and Gateway projection must evolve together. Do not redefine existing latitude/longitude or use arbitrary WKT as a substitute for a validated frame contract.

Each localization records event identity/time, observation and source IDs, frame revision, point/region/pose, optional floor/space/anchor/placement revisions, optional global projection, localization method, uncertainty and provenance. Use a tagged location variant with a strict dimension and bounded geometry; unknown, point, region and unresolved hypothesis are distinct states. Covariance declares axes and units and is validated for dimension, symmetry and positive semidefiniteness. Unknown accuracy remains unknown rather than the current normalizer’s zero default.

Resolve a placement by event time, retaining its recorded-time revision. Intervals for a source/placement purpose must not overlap without an explicit selection rule. Corrections append a new localization with supersedes and reason/actor; they never change the original observation or historical frame. Late data and revoked calibrations require explicit reprocessing, not silent movement of markers.

Moving a sensor creates a placement revision. Unmapped, invalid or unavailable calibration does not discard valid evidence; it remains unlocated and generates an observable failure. Invalid tenant/reference claims are rejected at the security boundary. High-rate localization uses compiled, bounded caches of validated placement/transform revisions; it never queries S3 or converts meshes for each detection.

A reader event does not prove a person’s subsequent trajectory. Entity tracking uses the existing authoritative identity or explicit hypothesis semantics, checks permissions on each disclosed entity, and does not join tracks solely because two points are close. Interpolation and prediction must be labeled and kept separate from observations.

Upload operations may negotiate bounded multipart capabilities; the API process does not buffer a complete upload or file, and quotas are enforced at initiation, finalization and reconciliation.

Real-time delivery, replay and zoom

Vision writes immutable localization and publication intent with the event transaction. It releases a localization into the spatial feed only after event permission relationships are acknowledged. A reconciler retries pending publication. No client can address a new event solely because its row exists.

Use a durable tenant-scoped change log and published spatial projection in PostgreSQL initially. Kafka wakes readers but is not the only record of an event that can be replayed. Do not create one Kafka consumer group per browser or assume a single sequence represents all Kafka partitions.

For the first implementation, a short per-tenant publication transaction locks a feed-head row, assigns contiguous sequence numbers for a bounded batch, and atomically writes projection changes, replay rows and the new head. Hold this lock only during publication, never during conversion, network calls or policy lookups. Sequence order then reflects committed publication, not event time. PostgreSQL sequences/BIGSERIAL alone do not provide this property: a higher number can commit before a lower one and cause missed resume data. Measure contention; a future sharded log requires a versioned vector cursor.

  1. Obtain a repeatable-read snapshot of the published projection and its feed head, pinning map/frame revisions and the normalized view filter. Materialize bounded snapshot membership or retain a short-lived snapshot session so pagination does not mix multiple SQL snapshots.
  2. Apply map/layer/event/entity visibility before disclosing results and issue an opaque cursor bound to tenant, principal, filter, snapshot, revisions and current authorization generation. Never embed visible Kafka offsets or unauthorized row IDs in client cursors.
  3. Replay changes after that head, then tail committed batches. Include localization IDs, monotonic delivery sequence and correction/retraction semantics. Clients deduplicate; transport is at least once, not exactly once.
  4. Re-check session expiry, membership, Cedar and resource visibility for every batch and before emitting results. Consume raw log pages independently of visible result count so denied records do not stall progress.
  5. Bound queue, snapshot lifetime and replay lag. Return RESET_REQUIRED on overflow, expired retention, policy generation changes, map deletion or incompatible view/revision changes. Resume from a fresh authorized snapshot.

Dynamic ACLs cannot be made transactional with a PostgreSQL snapshot. They require current checks; policy changes trigger a view reset, not a claim of perfect cross-system snapshot consistency. Retraction details are sent only while the recipient remains authorized. If access is lost, clear the authorized view without leaking which hidden event was removed. Event denial also denies its position, aggregate contribution and inferred entity track.

The authorization generation is a new invalidation contract, not an existing Gateway capability. All relevant writers must advance it through acknowledged membership, raw/event, map/layer and Cedar changes and a durable invalidation path. Until that path is complete, do not rely on cached positive decisions or claim generation-based revocation. Current per-batch checks remain mandatory; the native consistency/acknowledgement limitations documented in the authorization contract also apply here.

At country scale, return authorized aggregates/tiles under explicit point and time budgets; at building scale, points and floor/height filters. Apply authorization before counting or clustering. A precomputed tenant aggregate is unsafe for a user with only partial event access; start with bounded authorized queries or return VIEW_TOO_BROAD, not an approximate leaked count. Later security-cohort aggregates need their own revocation/rebuild contract.

Define live-view membership explicitly. Initial feeds pin a finite event-time window; a client advances it by obtaining a new snapshot/cursor. A later rolling window profile must emit expiry/removal changes and reconcile late arrivals. When corrected positions leave the viewport, retract the previous visible projection; when they enter, upsert it. Aggregate feeds require committed bucket replacement/deltas with the same replay rules, not just point insertions.

Authorization, audit and OTLP

Authorization and isolation

Add typed permissions to the canonical SpiceDB schema and Gateway enum before adding resolver side effects. Proposed permissions are tenant create_map, space view/manage, map view/edit/delete/share/manage, and spatial configuration manage. Separate restricted layers into typed resources when their visibility differs. Gateway is the sole relationship writer for these resources. Follow existing owner/editor/reader patterns with explicit tenant membership; accepting a tenant ID in a payload is never sufficient.

Displaying an overlay requires map/layer and event visibility; entity or anchor details require their own permissions. Permission on a plan does not grant permission to badge records, and a precise event position must not reveal a restricted room or anchor. Check referenced space/anchor visibility or redact the association and sensitive precision according to an explicit policy. All principals, including administrators, follow the structural resource checks. Cedar only restricts an existing allow, consistent with the current documented repair exemption for tenant custom policies.

Every cache, job, idempotency record, cursor and object key includes tenant. Caches containing event projections additionally bind the authorization/view scope; global tenant-only rendered event tiles are prohibited. Service jobs carry initiator and executor identities, purpose and expiry. Re-check delegated publication/destruction at execution rather than trusting an old allow. Separate service credentials, mTLS/mesh policy, Kafka ACLs and object-store IAM extend the existing zero-trust boundary.

Durable audit

Extend AuditAction with stable actions for map creation/upload/finalization, preparation, publication, georeferencing, anchor/placement changes, access changes, deletion, localization corrections and exports/subscription opening. Record attempted, denied/failed and succeeded outcomes, operation/request/trace IDs, tenant, initiating/executing identities, exact resource/revision, source digest, processing recipe and bounded failure category.

Record the immutable source-to-derived lineage and the event-to-calibration lineage separately. A trace may be sampled or expire while this provenance must remain reproducible. Do not log raw plans, precise trajectories, badge identities, tokens, signed URLs, arbitrary metadata or decoder exception text. Audit precise authorized data access by view/export/subscription scope rather than performing a synchronous SQL audit insert per marker or tile.

The current AuditStore::append starts an independent transaction; it cannot make a map publication and its audit record atomic. Introduce a transaction-aware append or transactional audit outbox for spatial state transitions. No sensitive mutation acknowledges success without durable audit intent. Reconciliation finishes abandoned operations with explicit outcomes. Existing immutable audit triggers and retention controls must remain enforced.

Operational telemetry

Follow the OTLP contract: logs, metrics and traces export only through the collector using bounded background queues. Resource names are galadril-gateway, galadril-vision, and galadril-spatial-worker; role/instance attributes do not change the service name.

Propagate W3C trace context in authenticated HTTP, job/outbox carriers and Kafka headers. Keep request and operation IDs in durable state. Long conversion, reconciliation and replay work uses span links to initiating context instead of keeping an HTTP span open for hours. External trace context does not establish authorization.

Budgets, delivery phases and acceptance gates

This architecture targets bounded-latency operational streaming, not hard real-time scheduling: SQL, Kafka, object storage and GC do not provide a hard deadline. Keep conversion outside the event path; reuse buffers and compiled transforms, stream assets, batch SQL/protocol work, avoid per-point heap-heavy JSON trees, and bound all caches and queues. Python conversion/blocking work runs in isolated processes/executors, not the asyncio event loop.

Phase 0: reviewable contracts

Deliver this architecture, settle format profiles and calibration conventions, then freeze SDL, manifest schema and additive observation schema with examples and compatibility fixtures. Confirm actual sample plans/models and acceptable position accuracy; without calibration data, camera-person localization remains an explicit unsupported capability. No frontend dependency is required.

Phase 1: complete local floor-plan backend

Implement map/space/frame metadata, private PNG/JPEG import, isolated preparation, versioned manifests, authenticated downloads, CRUD and asynchronous deletion. Add anchors and badge-reader placement, local event localization, bounded snapshot/replay and durable audit. This slice must prove a badge event remains at the same physical anchor across a map replacement and is still retained after deleting the map. It is a backend vertical slice, not upload-only CRUD.

Phase 2: geographic navigation and scale

Add complete georeferencing, geographic vector layers/tiles, viewport discovery, authorized aggregates and Earth/local transitions. Test dateline, polar coverage, height datums and zoom/detail budgets. Introduce prepared geographic raster profiles after native driver qualification and base-map provider configuration.

Phase 3: 3D buildings and large scenes

Accept validated GLB, qualify 3D Tiles ingestion/tiling, expose semantic feature references and precise calibration profiles. Add camera/depth localization only with tested uncertainty and validity semantics. BIM/CAD/point-cloud adapters remain separate capabilities rather than implicit promises.

Phase 4: operational scale and client integration

Benchmark peak rates, fan-out and conversion isolation; qualify both Linux architectures and crash recovery. Extract tile delivery or shard feed cursors only if measurements justify it. A later frontend can consume the same manifest, assets, snapshot and delta contract with its chosen renderer.

Remaining choices before enabling capabilities

The proposed first slice and service ownership can proceed without choosing a frontend renderer. The following choices affect later release gates:

  • Real upload fixtures: floor-plan resolution, model sizes, semantic room/door identifiers, target throughput and acceptable positional error.
  • Geographic datasets/provider rights, attribution, offline requirements and geographic coverage; this determines infrastructure cost beyond storing maps.
  • Supported calibration/height-datum profiles and trusted sensor placement ownership; a global position is unavailable until that contract is satisfied.
  • Converter implementations/licences and demonstrated native platform support for BIM, point clouds, terrain and very large 3D tiling.
  • Asset/evidence/audit retention and required revocation delay, which determine whether authenticated streaming can later be complemented by CDN capabilities.

These are bounded capability decisions. They do not justify silently accepting arbitrary formats, claiming uncalibrated camera detections are precise, or coupling the first backend to a specific rendering library.
