Mutation consistency boundaries

This audit follows the mutation families exposed by Gateway’s GraphQL schema through their application services and PostgreSQL adapters. A resolver delegating to one service is not, by itself, proof that the underlying operation is atomic. Likewise, a SQL transaction cannot roll back lakeFS, SpiceDB, object storage, Polis or SMTP effects.

Corrected binding operation

bindPluginOntology previously saved ontology_required through PipelineService::author, then independently called PutBinding. It now calls one authorized control-plane operation. The adapter sends the new AuthoringCommand::BindOntology through Registry’s existing pipeline command RPC.

Registry loads one tenant snapshot, validates the existing block, its published ontology and selector, modifies the draft and binding in memory, then commits the whole state with one expected revision. No external write occurs before that commit. Approval is cleared; the existing deployed release remains pinned. An older Registry rejects the unknown command before mutation. Generic public pipeline authoring rejects this internal command so it cannot bypass the binding authorization and audit path.

binding_and_required_contract_share_one_atomic_revision exercises an unavailable ontology, a stale head, an injected storage commit failure and a successful write. Rejected operations leave both the definition and binding list unchanged. The previous immutable revision also retains its original state.

The two direct pool queries found in Database::verify_security inspect role and RLS configuration; they are reads. Tenant business SQL uses Database::tenant, which begins a transaction and installs app.tenant_id with transaction-local scope. The audit found no reason to replace those existing local transaction boundaries with a transaction opened in schema.rs.

approved_roles_and_configuration_rollback_together_on_commit_failure installs a deferred PostgreSQL trigger that rejects the configuration commit. It verifies that neither the new role nor the mapping remains, then removes the fault and checks successful creation and tenant isolation against real PostgreSQL.

Rule for dependent writes

  1. Keep dependent writes under the domain owner in one command. Pass one SQL transaction through repository helpers instead of committing inside each helper. For Registry, mutate one snapshot and perform one compare-and-swap commit. A GraphQL request containing multiple mutation fields is not an atomic domain command.
  2. Across stores, persist an explicit operation or transactional outbox with the authoritative write. Record the intended projection, operation identity, tenant, revision and completion state before applying external effects.
  3. Replay must be idempotent and fenced against newer state. In particular, a delayed grant must not restore access that has subsequently been revoked. Never reuse an earlier authorization decision as proof for a later write.
  4. Report success only at the documented completion boundary. Distinguish an accepted, pending projection from a completely applied operation.
  5. Compensate only effects that remain safe to reverse. Retain durable recovery state for failed compensation and ambiguous outcomes. Sent mail, published evidence and ingested objects cannot be repaired by a blind delete.

The remaining cross-store rows above are explicit follow-up findings, not claims of atomicity or implementations of a general distributed transaction manager.
